# Changelog

## [0.7.0] - self-modification wire protocol, `recursion`/`feedback`/`memory`/`keep_source`, GPU parity

Крупный, до сих пор не закоммиченный блок работы поверх v0.6.1: сериализатор
для протокола самомодификации `RuleStore` (раньше был только десериализатор),
четыре новых расширения модели (`Rule::recursion`, `Rule::feedback`,
`Rule::memory`, `ShiftSpec::keep_source`/"излучение"), и портирование трёх из
них (плюс уже имевшийся `starvation_after`) на GPU-бэкэнд — который на v0.6.0
поддерживал только `cam` и обычный арбитраж, отвергая `recursion`/
`starvation_after`/`feedback`/`memory` целиком. Оказалось, что для трёх
последних причина отказа ("GPU не хранит состояние между тиками") была
решаемой (persistent storage-буферы, никогда не очищаемые между тиками), а не
фундаментальной; `recursion` же вообще не требовал межтикового состояния —
ложная причина отказа с самого начала. По ходу независимого (не просто
"второй бэкэнд для того же кода") портирования на GPU нашлось пять реальных
багов — четыре в новых GPU-проходах, один доказано ПРЕДСУЩЕСТВОВАВШИЙ в
CPU-движке, обнаруженный только благодаря побитовому сравнению с независимо
построенным GPU-путём.

### Added — протокол самомодификации `RuleStore`

- **Сериализатор** (`serialize_add_rule`/`serialize_remove_rule`/
  `serialize_clear_all`) — раньше в кодовой базе был только декодер пакетов
  (нужный для отправленных ИЗВНЕ правил), а собрать пакет из `Rule` было
  нечем. `serialize_add_rule` сам выбирает минимальный формат (обычный
  `AddRule` или расширенный `AddRuleExtended`) по тому, что реально нужно
  закодировать.
- `AddRuleExtended` (маркер `0xF2`) — расширенный формат пакета:
  `ext_flags` (бит0 = `cam`, бит1 = `recursion`) + опциональные 2-байтовые
  блоки `cam`/`recursion` перед секциями сдвигов/changes. Кодирует
  `Rule::cam` и `Rule::recursion` — та же структурная валидация, что и в
  `config::load_config` (`recursion`+`shifts` вместе отвергается,
  `max_depth == 0xFF` отвергается — коллизия с байтом-терминатором потока).
- Расширенное кодирование сдвигов/changes (общее для обоих форматов пакета):
  `ShiftSpec::broadcast` (квад `[0xFD, dir, steps, flags]`) и
  `ChangeValue::Ref` (квад `[0xFC, dx, dy, ref_index]`).
- **Явный, исчерпывающе задокументированный список НЕкодируемого** —
  `Rule::feedback`, `Rule::memory`, `ShiftSpec::keep_source` не имеют ни
  бита, ни байта нигде в протоколе (сериализатор возвращает `Err`, не
  тихо портит данные); байт `0xFF` где-либо в payload'е (обрезается ещё на
  этапе поиска терминатора потока, до разбора пакета); приоритеты
  `0xF0/0xF1/0xF2` для обычного `AddRule` (зарезервированные опкоды); первый
  `changes` сразу после id/последнего сдвига со смещением `dx = -2/-3`
  (коллизия с флагами сдвига); `changes` со смещением `dx = -4` в любой
  позиции (коллизия с флагом `ChangeValue::Ref`).
- ~26 новых тестов: roundtrip для broadcast/Ref/cam/recursion, ручная сборка
  пакетов, все перечисленные отказы, регрессия "старые хардкодные пакеты
  декодируются побитово так же, как раньше", явный тест "протокол НЕ может
  выразить feedback/memory/keep_source", end-to-end тест самомодификации,
  подтверждающий, что принятое правило никогда не материализует эти четыре
  расширения.

### Added — новые возможности модели (CPU)

- `Rule::recursion` (`RecursionSpec { max_depth, direction }`) — ограниченный
  каскад ВНУТРИ одного тика: после обычных фаз "сдвиги"/"changes" новая Фаза 3
  в `apply_rule_buffered` заново проверяет паттерн правила, сдвинутый на
  `k × direction` для `k = 1..=max_depth`, и применяет `changes` на каждом
  уровне, где паттерн всё ещё совпадает — читая уже НАКОПЛЕННЫЙ этим же
  каскадом буфер записи (`read_cell_effective`/`read_age_effective`/
  `pattern_matches_effective`), единственное намеренное исключение из
  "detect всегда читает pre-tick состояние", ограниченное одним уже
  выигравшим арбитраж матчем. `conflict_analyzer::compute_rule_data`
  расширен: статическая граница записи — объединение по всем `k=0..=max_depth`
  вдоль `direction` (Corollary B).
  - `cam` + `recursion` вместе — каскад НЕЗАВИСИМЫХ магнитов вдоль
    `recursion.direction`, каждый со своим собственным диском поиска
    (`apply_cam_buffered`, `search_nearest_effective`). Статическая граница —
    объединение дисков по уровням. `arbitrator::get_match_affected_cells`
    для этой комбинации использует консервативный `write_cells` вместо
    точного 2-клеточного пути (ячейки каскада процедурно зависят от порядка
    применения, неизвестного на этапе арбитража — сознательно закрытый риск
    занижения площади, не просто защитная мера).
  - `recursion` + `min_age > 0` — разрешено, `min_age` проверяется на
    КАЖДОМ уровне каскада.
  - `memory` (`NeighborType`) + `recursion` — разрешено, у каждого уровня
    каскада своя независимая память с ключом `(ox, oy, rule_idx)`;
    `memory` (`RuleOutcome`) + `recursion` — явно отвергается
    (`config.rs`): у уровня каскада нет отдельного шага арбитража,
    "выиграл/проиграл" для него структурно не определено.
- `Rule::feedback` (`FeedbackSpec { timeout, new_direction }`) — правило
  РОВНО с одним сдвигом переключает направление НАВСЕГДА (защёлка,
  `saturating_add`, никогда не сбрасывается) после `timeout` тиков подряд
  обнаружения матча (считаются попытки, не поражения). Новое состояние
  движка — `Engine::feedback_counters`.
- `Rule::memory` (`MemorySpec { window, record_trigger, match_pattern }`,
  `RecordTrigger::{NeighborType(dir), RuleOutcome}`) — FIFO-гейт: правило
  участвует в арбитраже, только когда его буфер наблюдений ПОЛОН и совпадает
  с `match_pattern` поэлементно; буфер продолжает наблюдать даже пока гейт
  закрыт. `NeighborType` пишет ДО арбитража (тип соседа, pre-tick), `RuleOutcome`
  — ПОСЛЕ (исход арбитража этого матча). Новое состояние движка —
  `Engine::memory_buffers`.
- `ShiftSpec::keep_source` / `ShiftSpec::emit(direction, steps)`
  ("излучение") — сдвиг, не очищающий исходную клетку: значение копируется,
  а не перемещается. Ортогонален `broadcast`. `conflict_analyzer` намеренно
  не менялся — исходная клетка остаётся в статической границе записи как
  безопасное завышение.
- Оба (`feedback`/`memory`) поддерживают перенос своего persistent-состояния
  на новую позицию при выигранном сдвиге (`apply_shift_buffered`) — без
  этого состояние обнулялось бы каждый тик, поскольку маркер физически
  двигается.

### Added — GPU backend (feature `gpu`)

- `Rule::recursion` на GPU — каскад оказался чисто ЛОКАЛЬНЫМ, однопоточным
  вычислением (каждый уровень читает клетку на статически известном
  смещении, используя ТОЛЬКО уже накопленные этим же матчем ячейки —
  межпоточная синхронизация не нужна), а не блокером, как считалось раньше.
  `MAX_RECURSION_DEPTH=4`; `cam`+`recursion` вместе по-прежнему вне
  GPU-подмножества (`CamRecursionUnsupported` — рантайм-поиск на каждом
  уровне каскада, отдельный, не реализованный здесь путь).
- `Rule::starvation_after` на GPU — persistent storage-буфер счётчиков,
  `update_starvation_pass` (reset-on-win/рост-on-loss/reset-on-orphan),
  дispatch'ится ПОСЛЕ гибридного CPU-добора. Порог `0` — реальный, отличный
  от "выключено" случай, закодирован отдельным флагом `has_starvation`.
- `Rule::feedback` на GPU — persistent-защёлка + перенос на новую позицию,
  ДВА раздельных прохода (латч → перенос, не один — перенос пишет в слот
  ДРУГОЙ клетки, что было бы гонкой с осиротевшим сбросом того же слота её
  собственным потоком в одном проходе). `feedback`+`broadcast` вне
  подмножества.
- `Rule::memory` на GPU — persistent FIFO-буфер (окно ≤4) + счётчик
  заполненности; гейт — ЧИСТЫЙ pre-арбитражный фильтр (новый флаг
  `GpuMatch::structural`, отдельный от `matched`, который для memory-правил
  теперь значит "гейт открыт"). Оба триггера поддержаны.
  `memory`+`recursion` (любой триггер) и `memory`+`cam` вне подмножества —
  по-каскадный гейтинг и отдельная CAM-ветка не реализованы здесь.
- Новая защитная проверка: `feedback`/`memory` + `changes` на ТОМ ЖЕ
  относительном смещении, что и цель сдвига — вне подмножества
  (`FeedbackChangeCollidesWithShiftTarget`/`MemoryChangeCollidesWithShiftTarget`).
  Перенос persistent-счётчика на GPU вычисляет новый слот через
  `slot_in_cell`, ПРЕДПОЛАГАЯ, что тип клетки на новой позиции останется
  типом самого маркера — ложно, если `changes` (побеждающий `shifts` при
  конфликте клетки) реально пишет туда что-то другое; в худшем случае
  перенесённый счётчик попадает в слот СОВЕРШЕННО ДРУГОГО правила и портит
  его состояние. CPU иммунен (ключ переноса — самоописывающийся
  `(x, y, rule_idx)`), GPU — нет.
- `ShiftSpec::keep_source` — явно вне GPU-подмножества
  (`KeepSourceUnsupported`), не тихо отбрасывается.

### Fixed

- `arbitrator::get_match_affected_cells`: cam+recursion матчи занижали
  реально затрагиваемую площадь (использовали только 2 ячейки CAM-эффекта
  вместо консервативного объединения по всему каскаду) — два невраждующих
  по старой проверке матча могли тихо испортить общее состояние.
- `Engine::starvation_counters` (в отличие от `feedback`/`memory`) никогда
  не чистился при исчезновении матча — застывший счётчик "K поражений
  подряд" при повторном появлении того же матча возобновлял отсчёт со
  старого значения, давая правилу выиграть РАНЬШЕ положенного по его же
  гарантии. Обобщено в новый общий блок очистки осиротевших записей
  (`feedback_counters`/`memory_buffers`/`starvation_counters`), намеренно
  расположенный ДО раннего выхода при пустом `matches` — исчезновение
  последнего матча особенно важный случай для очистки, не повод её
  пропустить.
- Новый `ExtensionFlags` (считается один раз при создании/перестройке
  движка): раньше сканы под `starvation_after`/`feedback`/`memory`
  безусловно платили O(число матчей) HashMap-лукапов каждый тик, даже если
  ни одно правило набора эти поля не использовало — вопреки заявленным
  "нулевым накладным расходам".
- `build_memory_spec` не проверяла, что `match_pattern`'s варианты
  `RecordedValue` соответствуют форме, которую `record_trigger` вообще
  способен произвести (`NeighborType` пишет только `Type(_)`, `RuleOutcome`
  — только `Applied`/`Missed`) — рассогласованный конфиг загружался без
  ошибки, но гейт не мог открыться никогда.
- GPU `cpu_fallback_resolve` (гибридный добор несошедшихся за раунды
  матчей) писал только итоговые значения ячеек, но не финальный
  ACCEPTED/REJECTED обратно в `match_state` — матчи, доигранные на CPU,
  навсегда оставались PENDING(0) с точки зрения `update_starvation_pass`.
- GPU `update_starvation_pass`/`update_feedback_latch_pass`: после
  добавления `memory` флаг `matched` стал означать "гейт открыт", а не
  "структурно совпало" — обе проверки ошибочно трактовали ВРЕМЕННО
  закрытый гейт как "матч осиротел" и сбрасывали персистентный
  счётчик/защёлку, хотя CPU в этом случае их вообще не трогает (заморожены,
  не сброшены). Правило со `starvation_after`/`feedback` + `memory` могло
  никогда не пересечь свой порог там, где CPU надёжно бы его пересёк.
  Исправлено новым флагом `GpuMatch::structural`, отдельным от `matched`,
  всегда равным ему для НЕ-memory правил (обратная совместимость по
  построению).
- **CPU, `run_tick_with_cache`**: инкремент `feedback_counters` стоял МЕЖДУ
  чтением счётчика арбитражем (`arbitrator::get_match_affected_cells`,
  решает эффективное направление сдвига ДЛЯ ЦЕЛЕЙ КОНФЛИКТ-ПРОВЕРКИ) и его
  же чтением при apply (`applicator::apply_rule_buffered`, решает
  эффективное направление ДЛЯ РЕАЛЬНОЙ ЗАПИСИ). На тике, где счётчик матча
  ПЕРЕСЕКАЕТ `timeout` ИМЕННО на этом тике, арбитраж резервировал клетки
  для СТАРОГО (ещё не защёлкнутого) направления, а apply реально писал в
  НОВОЕ — цель, которую арбитраж НИКОГДА не проверял на конфликт с другими
  матчами; при независимо принятом конкуренте на этой цели победитель
  решался порядком записи apply, а не арбитражем, и матч с `feedback` мог
  тихо ИСЧЕЗНУТЬ (source-clear проходил, целевая запись проигрывала
  необнаруженную гонку). Найдено побитовым сравнением с независимо
  построенным GPU-путём. Правильный фикс — оба чтения ОБЯЗАНЫ видеть
  счётчик КАК ОН БЫЛ на начало тика (та же дисциплина, что уже держат
  `age`/`min_age`/`starvation_counters` — обнаружение ЭТИМ тиком становится
  видимым только СЛЕДУЮЩЕМУ, не задним числом влияет на решение этого же
  тика): инкремент теперь происходит ПОСЛЕ apply, не между чтениями. Для
  выигравших и сдвинувшихся матчей — прямо внутри
  `applicator::apply_rule_buffered`, СРАЗУ после чтения и ДО применения
  сдвига (простой единый проход после apply гонится с собственным
  переносом счётчика `apply_shift_buffered` на новую позицию — создаёт
  постороннюю запись на уже покинутой клетке вместо инкремента реальной);
  для проигравших — отдельным проходом в `run_tick_with_cache` (их позиция
  гарантированно не переносится, apply для них не вызывается). Наблюдаемое
  следствие: переключение на `new_direction` вступает в силу СО
  СЛЕДУЮЩЕГО тика после `timeout`-го обнаружения, не на нём самом.
  GPU-сторона (`shader.wgsl`) при этом УПРОСТИЛАСЬ — снята "+1"-поправка,
  добавленная ранее в этой же сессии специально под старую (как выяснилось,
  неверную) семантику CPU: GPU читает persistent-счётчик напрямую, ровно
  как уже делает `starvation_counters`.

### Changed / Resolved

- `memory`+`recursion`: было блэнкет-исключено целиком; `NeighborType`
  триггер оказался поддержим (каждый уровень каскада — самостоятельная
  позиция со своим собственным гейтом, тот же приём, что уже применён к
  `recursion`+`min_age`), `RuleOutcome` остаётся исключённым — структурно,
  не просто сложно реализовать.
- `keep_source`-каскад (цепочка "излучающих" правил) исследован на предмет
  "стопорится навсегда": подтверждено как реальная динамика (наивный
  age-based тай-брейк всегда предпочитает старую исходную клетку свежей
  копии), не баг движка — задокументирован рабочий обходной паттерн
  (front-gate условие "моя цель сейчас пуста").
- Обратимость (Theorem 9, конструктивно, новые примеры
  `examples/proof_reversibility_{feedback,keep_source,keep_source_cascade,memory,recursion}.rs`):
  `feedback` и `keep_source` (одиночный) ломают наивный `R⁻¹` (скрытое
  состояние вне решётки / копия — не обратная операция копии
  соответственно), но оба чинятся другим рецептом (запись-и-воспроизведение
  истории; "стирающее" правило). `Rule::memory`: `NeighborType` обратим тем
  же рецептом, что и `feedback`; `RuleOutcome` доказано НЕ восстановим из
  одних только дельт решётки (конструктивный контрпример — два набора
  правил с побитово идентичной решёткой, но навсегда разошедшейся
  внутренней историей `Applied`/`Missed`). `recursion` не ломает Theorem 9
  вовсе (нет скрытого состояния, нет сдвига для обращения).
- Новый пример `examples/proof_distance_priority_routing.rs` — маршрутизация
  токена кратчайшим путём вокруг препятствия через приоритет-по-расстоянию
  (BFS-волна, закодированная типом клетки, конкурирующие сдвиговые правила),
  без CAM и без новых полей движка; сверено с независимо посчитанным BFS.

### Added — конфигурация и наблюдаемость движка

- `YamlConfig.version: Option<u32>` (`#[serde(default)]`) — отсутствие поля
  трактуется как версия 1; несовпадение версий — `CellariaError::Config` с
  обеими версиями в тексте. `load_config` разделён на тонкий
  `load_config(path)` + чистый `load_config_str(&str)` (тестам не нужен
  файловый I/O).
- `conflict_analyzer::analyze_conflicts(&RuleIndex) -> ConflictReport` — та же
  машинерия `ConflictGraph::build`, что и у статического анализатора, но
  маппит плоские индексы графа обратно на человекочитаемые пары
  `(head, local rule_idx)`. Вызывается явно из `main.rs` после
  `load_config`.
- `GpuEngine::with_rounds(width, height, cells, rule_index, rounds)` —
  дополнительный конструктор рядом с `GpuEngine::new` (теперь вызывает
  `with_rounds(..., ROUNDS)`); `ChunkStorage::with_chunk_size(n)` — рядом с
  `ChunkStorage::new()`. `MAX_WRITE_CELLS`/`MAX_BROADCAST_REACH` сознательно
  не вынесены — зашиты в шейдер, не рантайм-параметр.
- `Engine::enable_tick_logging()` / `Engine::tick_log() -> Option<&[TickLogEntry]>`
  — тот же opt-in нулевой-по-умолчанию паттерн, что и у
  `enable_input_recording`/`TickPhaseTimings`. `TickLogEntry { tick, accepted,
  rejected, starvation_events, feedback_events }` сериализуется напрямую
  через `serde_json` (плоская структура, не задета проблемой нестроковых
  ключей `HashMap`, см. ниже про `EngineSnapshot`). `starvation_events`/
  `feedback_events` считают кандидатов "под наблюдением" в этот тик
  (структурное совпадение + соответствующее поле `Rule` задано), не только
  реально сработавших — дешевле и достаточно для мониторинга.

### Added — сохранение и воспроизведение состояния

- **`RuleStateStore`** (`src/engine/rule_state.rs`) — объединяет
  `starvation_counters`/`feedback_counters`/`memory_buffers`/
  `activation_counters` за одной точкой доступа с дисциплиной снимка тика
  (2.2.1), теперь закреплённой заимствованием компилятора, а не только
  соглашением: `snapshot() -> RuleStateSnapshot` (только `&`, для чтения
  "как было на начало тика") и `mutate()` (только после того, как ни один
  `snapshot()` больше не жив) — получить оба одновременно не даёт borrow
  checker, не ревью.
- `Engine::snapshot(&self) -> EngineSnapshot<S>` (требует `S: Clone`, не
  потребляет `self`) / `Engine::from_snapshot(EngineSnapshot<S>) -> Engine<S>`
  — полное состояние движка (решётка, `rule_index`, весь `RuleStateStore`)
  для сохранения/восстановления. Сериализация — `serde_yaml`, не
  `serde_json`: у модели данных нестроковые ключи `HashMap` почти всюду
  (`(x, y)`, `(head, rule_idx)` и т. п.), которые `serde_json` в принципе не
  умеет сериализовать.
- `Engine::replay(snapshot: EngineSnapshot<S>, log: &[InputEvent], target_tick: u64)`
  — восстановление из снимка + журнала входных событий, проигрывание вперёд
  до `target_tick`. Попутно найден и исправлен реальный баг в
  `specs/specification.md`, написанной ранее в той же сессии: Input НЕ
  автоматическая часть `run_tick()` — это отдельный, явно вызываемый
  `apply_input()` (5.1/8.1 специфики), который `replay` обязан вызывать сам
  на каждом тике перед `run_tick()`, а не полагаться на то, что `run_tick()`
  подхватит очередь. Обнаружено не сразу — слабый тест дважды вакуумно
  проходил мимо этой ошибки, поймано только `panic!()`-отладочным принтом.
- Два multi-tick property-теста (детерминизм повторных прогонов,
  непрерывность `snapshot`→`from_snapshot`) — ловят именно тот класс багов,
  который эта сессия находила чаще всего (рассинхронизация состояния между
  тиками). Property-покрытие `recursion`/`cam` сознательно не строилось —
  отложено, не забыто; закрыто позже той же сессией, см. ниже.

### Added — `Rule::max_activations`

- `Rule::max_activations: Option<u32>` — глобальный (не привязанный к
  позиции) бюджет побед: правило перестаёт участвовать в арбитраже, как
  только суммарное число его побед за всё время достигло лимита, независимо
  от того, в какой клетке оно сработало. Ключ счётчика — `(head, rule_idx)`,
  не `(x, y, rule_idx)` — в отличие от `feedback`/`memory`/
  `starvation_after`, не нуждается в переносе состояния при сдвиге и не
  участвует в позиционной чистке осиротевших записей (`extension_rule_indices`);
  устаревание счётчика при смене состава правил покрыто отдельно,
  `Engine::invalidate_stale_extension_state`. Гейт читает счётчик КАК ОН БЫЛ
  на конец предыдущего тика (та же дисциплина 2.2.1, что и у остальных
  расширений), инкремент — после арбитража, по `accepted` напрямую.

### Changed / Resolved — производительность горячего пути тика

Отдельный раунд измерений по прямому запросу: не "дай идеи", а "вот текущие
цифры по каждой фазе (detect/arbitrate/apply)" на реалистичных сценариях
(CF — шахматка встречных сдвигов, CA — сплошная "пробка" из клеток,
двигающихся в стену), с последующей проверкой и реализацией только того,
что подтвердилось прямым измерением. Общая методологическая находка,
всплывавшая трижды за сессию: **изолированный микробенчмарк на
синтетических (пред-отсортированных/пред-заполненных) данных может
убедительно подтвердить неверную гипотезу** — сравнение всегда велось
против ПРОГРЕТОГО персистентного baseline на РЕАЛЬНОМ порядке данных, не
холодного/синтетического.

**Реализовано и подтверждено:**

- Слияние `filter`+`fold` в detect и устранение клонирования `accepted`
  через срез (вместо `Vec`-копии) — детект и apply дешевле на 34-46%
  (детект) и 29-34% (apply) на CF/CA (`Engine::run_tick_profiled`,
  контролируемый A/B).
- `write_buffer`/`pattern_buffer` — персистентные поля `Engine`
  (`.clear()`+`&mut` вместо `Vec`/`HashMap::new()` на каждый вызов
  `apply_matches_with_cam`/`apply_rule_buffered`). Сабо­таж-верифицировано
  (`.clear()` пропущен → 2 property-теста немедленно упали). После всех трёх
  правок apply на CF доминирует уже не так безоговорочно (73%→~69%), на CA
  как доминировал arbitrate, так и доминирует — ожидаемо, ни одна из правок
  его не касалась.
- `HeadRuleIndex` (`[Option<&Vec<Rule>>; 256]`, `mod.rs`) вместо
  `rule_index.get(&head)` — `CellType` оборачивает `u8` (256 значений),
  хэширование не нужно вообще. Строится один раз за вызов горячей функции
  (НЕ персистентное поле `Engine` — заимствует у `rule_index`-параметра,
  самоссылающаяся структура была бы нужна для персистентности). Честный A/B
  (переключение только реализации `lookup_rule`, ни один вызывающий код не
  менялся): apply стабильно дешевле (~109-128мс vs ~138мс на CA-пробке),
  arbitrate — та же тенденция, но зашумлённее (вторая, на тот момент ещё не
  тронутая `CellType`-ключевая карта `rule_cache: RuleDataCache` — закрыта
  тем же приёмом, см. ниже).
- `thread_local!`-персистентность для `used_cells`/`affected`/`keyed` в
  `arbitrate_with_cam` (`arbitrator.rs`) — `Engine`-поле сюда не подходит:
  функция вызывается ПАРАЛЛЕЛЬНО по полосам через rayon (до ~25 раз за тик
  на CA), `thread_local!` даёт каждому rayon-воркеру свой персистентный
  буфер, переживающий вызовы между полосами И между тиками на этом потоке.
  `used_cells`/`affected`: -65.2% изолированно, реальный эффект на CA —
  arbitrate ~23мс (холодный тик 0) → ~12-16мс (тёплые тики 1-7). `keyed`:
  -30.6% изолированно. Оба сабо­таж-верифицированы; для `keyed` диверсия
  (`.clear()` в начале убран) НЕ поймана ни одним тестом — оказалось, что
  `.drain(..)` в конце той же функции уже безусловно опустошает буфер к
  следующему вызову, `.clear()` здесь защитный, но доказуемо избыточен (в
  отличие от `used_cells`, где та же диверсия ломала 20 тестов) — оставлен
  как defensive-практика, честно задокументирован как таковой.
- Глобальный аллокатор заменён на `mimalloc` (`Cargo.toml`, `#[global_allocator]`
  в [lib.rs](src/lib.rs:90)) — на CA-пробке все три фазы тика (detect/
  arbitrate/apply) дешевле на ~30-40% одновременно, без единой правки в
  горячем коде (3 прогона в каждую сторону, устойчиво). Забирает бОльшую
  часть выигрыша, ради которого рассматривалась bump-арена на весь тик, почти
  без инвазивности. Найдено при последующей ревизии: `#[global_allocator]`
  безусловно на всю библиотеку сломал бы любого потребителя `cellaria`-как-
  зависимости, желающего свой аллокатор (объявляется РОВНО ОДИН РАЗ на весь
  финальный бинарник, конфликт неразрешим со стороны потребителя) — вынесено
  за default-on фичу `mimalloc-alloc`, `default-features = false` снимает
  декларацию целиком, не трогая `gpu`.
- **Закрыт follow-up, отмеченный выше:** `RuleDataCache` (`conflict_analyzer.rs`)
  переведена с `HashMap<(CellType, usize), RuleData>` на `[Option<Vec<RuleData>>; 256]`
  — тот же приём, что и `HeadRuleIndex`, но, в отличие от него, персистентная
  ВЛАДЕЮЩАЯ структура (`Engine::rule_cache`, перестраивается только при
  смене состава правил, не каждый тик — самоссылающейся структуры нет и не
  требуется). `compute_conflict_partners`'s `rule_cache.values()` адаптирован
  под новую форму (`.iter().filter_map(...).flat_map(...)`). Публичный API
  (`get_rule_data`/`build_rule_data_cache`) не изменился, `Engine::rule_cache`
  сменил только внутренний тип (не было внешних потребителей раз `HashMap`
  напрямую — проверено). Измерено на CA-пробке поверх уже применённых
  `HeadRuleIndex`+`mimalloc`: arbitrate/apply ещё немного ниже (~10-12мс/
  13-15.5мс → ~8-11.5мс/10-12.4мс). Полный suite зелёный (252+23+13+7).
- **Закрыт весь список открытых архитектурных вопросов** (specs/architecture.md
  §11) — по каждому либо реализация, либо окончательное решение не делать:
  - Рекурсивное деление boundary-полосы — вторая попытка, депт-ограниченная
    (`MAX_BAND_SPLIT_DEPTH=4`) версия с jitter (чередование числа полос по
    чётности глубины рекурсии, чтобы сбить резонанс периодов, погубивший
    первую наивную попытку). Терминацию гарантирует, корректность
    подтверждена (property-тесты spatial-vs-централизованный арбитраж
    зелёные), но контролируемый A/B на CA-пробке реального выигрыша не
    показал (arbitrate не изменился, apply чуть хуже — лишний rayon-
    диспетчинг/аллокации на уровень рекурсии стоят больше jitter'а).
    Откачено полностью, обе попытки задокументированы в `arbitrator.rs`.
  - Протокол самомодификации, приоритеты 240-242 — при перепроверке
    оказалось, что УЖЕ РАБОТАЕТ: `serialize_add_rule`'s `needs_ext`
    автоматически переключается на `AddRuleExtended` для этих трёх значений
    (приоритет там отдельным байтом, не дискриминатором), уже покрыто
    существующим тестом. Ничего не чинилось — предыдущая формулировка этого
    пункта была неточной. Приоритет 255 остаётся недостижим по отдельной,
    более глубокой причине (терминатор-скан режет ЛЮБОЙ payload-байт 0xFF,
    не только priority) — не фиксится точечно, оставлено как есть.
  - GPU+CPU async pipelining и SoA-раскладка решётки — осознанные решения
    НЕ делать сейчас (первое требует отдельного дизайн-прохода сравнимой
    сложности с VecSink, второе — breaking-переписывание `GridStorage`
    ради выигрыша, не оправданного текущим масштабом узкого места).
    Рассмотренная более дешёвая альтернатива для второго (сузить
    `born_at: u64` → `u32`) отклонена без реализации: тоже breaking, нулевой
    измеренный выигрыш, риск переполнения после ~4 млрд тиков.
- **Закрыта дыра в property-покрытии, отмеченная выше:** `tests/property_recursion_cam.rs`
  — те же два инварианта (детерминизм повторных прогонов,
  `snapshot`/`from_snapshot`-непрерывность), что уже проверялись для
  `starvation_after`/`feedback`/`memory`/`max_activations`, теперь и для
  `cam`/`recursion`/`cam`+`recursion` вместе. Генератор построен заново под
  их структурные ограничения (`config.rs`'s валидация: `cam`/`recursion`
  оба требуют `shifts.is_empty()`, `cam`+`recursion` вместе разрешены,
  `memory(RuleOutcome)`+`recursion` запрещено — генератор избегает этой
  комбинации по построению, а не полагается на то, что `Engine::new`,
  строящий движок напрямую из `Rust`-структур в обход `config::load_config`,
  её вообще отловит). Сабо­таж-верифицировано: убрал уже известный
  load-bearing `used_cells.clear()` (`arbitrator.rs`) — оба новых теста
  немедленно упали, подтверждая, что генератор реально доходит до
  `thread_local!`-буферов через cam/recursion-формы правил, не только
  тривиально проходит. Полный suite зелёный (252+23+13+7+2).

### Fixed — реальный баг в `arbitrate_spatial_with_cam` (не гипотетический)

Найден при закрытии дыры в property-покрытии выше: генератор
`recursion`/`cam` в масштабе, где включается spatial band-split
(`SPATIAL_THRESHOLD=4096`), сразу выявил расхождение с централизованным
арбитражем на реальном (не сабо­тажированном) коде.

- **Суть:** `core` (арбитрируется параллельно по полосам) и `boundary`
  (арбитрируется отдельно, сам с собой, последовательно) раньше просто
  СКЛЕИВАЛИСЬ (`result.extend(...)` для обоих) — без единой перекрёстной
  проверки. `margin = 2×reach` (Lemma 6, специф. §10.7) доказывает только
  "core-матчи из РАЗНЫХ полос не пересекаются" — про boundary-против-
  соседнего-core (в том числе того же самого band'а) теорема ничего не
  говорит: boundary-матч прямо на границе своей зоны физически может
  писать ещё на `reach` клеток дальше, вглубь соседней core-зоны.
  Конструктивно доказано, что НИ ОДИН конечный margin с простой пороговой
  схемой (`dist >= margin ⟹ core`) не может это исключить для любого
  `reach >= 1`.
- **Почему не ловилось раньше:** ВСЕ существовавшие Lemma-6-тесты
  использовали правила с записью в одну точку (без сдвигов, без
  `recursion`) — точка не может дотянуться через границу вне зависимости
  от margin. `recursion` (см. выше) стало первым правилом в истории
  тестов проекта с реальной многоклеточной записью на масштабе, где
  boundary-путь вообще включается.
- **СЕРЬЁЗНОСТЬ ВЫШЕ, ЧЕМ КАЗАЛОСЬ ПЕРВОНАЧАЛЬНО** — проверено ОТДЕЛЬНО
  (`test_arbitrate_spatial_matches_centralized_plain_shift_dense_overlapping_writes`,
  `property_arbitration.rs`): баг ловится и на ОБЫЧНОМ одиночном сдвиге
  (`shifts`, без `recursion`, без `cam`) — самом частом случае в принципе,
  плотная упаковка анкоров, спровоцировал расхождение 1200 vs 1219 на
  ТОЙ ЖЕ реинтродукции исходного кода. Значит CA-"пробка" (сплошной сдвиг
  вправо, 300×300), которую эта сессия гоняла ВЕСЬ ДЕНЬ ради замеров
  производительности (`Engine::run_tick_profiled`, десятки прогонов,
  ~44000+ принятых матчей за тик — далеко за `SPATIAL_THRESHOLD=4096`),
  могла ВСЁ ЭТО ВРЕМЯ тихо принимать конфликтующие записи — просто никто
  не сверял содержимое решётки с централизованным эталоном, только время.
  Баг не специфичен для `recursion`/`cam` — это фундаментальная проблема
  самого band-split алгоритма, задевающая любой конфиг с достаточно плотной
  конкуренцией НА ЛЮБОМ `reach >= 1`, включая простейшие CA-подобные
  сценарии. `recursion` просто оказалась первым правилом, ДОСТАТОЧНО
  придирчиво проверенным (property-тест на реальном масштабе), чтобы это
  обнажить.
- **Конкретный репро:** x=7 (boundary) и x=8 (core), запись обоих по 4
  клетки (recursion), пересечение на {8,9,10} — оба были приняты
  централизованным-несовпадающим набором. Тест остался в suite:
  `tests/property_arbitration.rs::test_arbitrate_spatial_matches_centralized_recursion_dense_overlapping_writes`.
- **Фикс:** каждая полоса арбитрирует СВОЙ ПОЛНЫЙ core-набор целиком, как
  раньше (первая попытка фикса разделяла core на "safe"/"at_risk" ДО
  арбитража — это сломало сравнение двух core-матчей ОДНОЙ полосы,
  близких к границе, друг с другом — новый баг вместо старого, найден и
  исправлен в процессе той же сессии). Из уже принятых результатов каждой
  полосы: матчи с `dist >= margin+reach` от ОБЕИХ границ (`safe_margin`)
  доказанно недостижимы никаким boundary-матчем — финальны без проверок;
  остальные core-победители (узкая "рискованная" зона шириной `reach`)
  идут ОДНИМ дополнительным проходом `arbitrate_with_cam` вместе с
  `boundary`, тем же тотальным порядком.
- **Цена:** первая (наивная, "слить весь core обратно") версия фикса
  давала измеренную регрессию ~30-50% на CA-пробке даже для `reach=1`, где
  риска никогда не было — реализованная (targeted) версия — в пределах
  шума от исходной производительности (~9.6-14.1мс vs исходных ~8-11.5мс).
- **Остаточный теоретический риск, не закрытый этим фиксом** (см.
  `specs/architecture.md` §11 п.5): узкий 3-сторонний сценарий конфликта
  (at_risk-победитель проигрывает boundary в финальном проходе, а более
  слабый локально-отвергнутый кандидат ТОЙ ЖЕ полосы уже не переигрывается)
  — не воспроизведён ни на одном тесте, но и не доказан невозможным.
  Задокументирован честно, не заметён под ковёр.
- **Фикс дополнительно проверен на `cam`** (`src/engine/tests.rs`'s
  `test_arbitrate_spatial_matches_centralized_cam_dense_overlapping_writes`,
  `CamPositions` — `pub(crate)`, тест внутренний, не в `tests/`) — тот же
  класс стресс-теста (плотная гарантированная 2-клеточная коллизия каждой
  соседней пары, >4096 матчей), что нашёл баг для `recursion`, но для
  ПРИНЦИПИАЛЬНО другого пути вычисления affected-региона (точный
  `[found, magnet]`, не консервативный union дисков). Сабо­таж-верифицирован
  (реинтродукция исходного blind-union бага немедленно поймана,
  1626 vs 1654 принятых). Подтверждает: фикс обобщается, `reach` из
  консервативного `RuleData::bbox` остаётся корректной верхней границей и
  для точного `cam`-региона. Полный suite зелёный (253+23+13+10+2+2).
- **Систематически проверены ВСЕ расширения модели на тот же класс бага**
  (плотная гарантированная коллизия, >4096 матчей, сабо­таж на исходном
  коде для каждого):
  - **Обычный одиночный сдвиг** (без `recursion`/`cam`/`feedback`) —
    `test_arbitrate_spatial_matches_centralized_plain_shift_dense_overlapping_writes`
    (`property_arbitration.rs`). ПОЙМАЛ баг тоже (1200 vs 1219) — САМЫЙ

    edge-case'ом, а фундаментальной проблемой самого алгоритма band-split
    при любом `reach >= 1`. Прямое следствие: CA-"пробка" (300×300,

    производительности (`Engine::run_tick_profiled`, ~44000+ матчей за
    тик — далеко за `SPATIAL_THRESHOLD=4096`), могла ВСЁ ЭТО ВРЕМЯ тихо
    принимать конфликтующие записи — сверялось только время, не
    содержимое решётки.
  - **`feedback`** — `test_arbitrate_spatial_matches_centralized_feedback_dense_overlapping_writes`
    (`src/engine/tests.rs`, внутренний — `FeedbackCounters` `pub(crate)`).
    Единственное расширение с СОБСТВЕННОЙ (не через общий
    `rule_data.write_cells`) веткой в `get_match_affected_cells` — точные
    `feedback_normal_write_cells`/`feedback_alt_write_cells` по состоянию
    защёлки, а не консервативный union. ПОЙМАЛ баг тоже (1626 vs 1654,
    та же диверсия). Фикс работает и для этой ветки.
  - **`keep_source`** — НЕ тестировался отдельно, проверено чтением кода:
    `compute_write_cells` включает клетку `(0,0)` БЕЗУСЛОВНО, даже при
    `keep_source: true` (не очищается физически, но остаётся в границе
    консервативно) — геометрически идентично обычному сдвигу, тот же
    generic-путь в `get_match_affected_cells`. Отдельный тест был бы
    избыточен с plain-shift-тестом.
  - **`broadcast`-сдвиги** — НЕ тестировался отдельно, тот же аргумент:
    `broadcast_path_cells` даёт статический (не runtime-зависимый) набор
    клеток пути, идёт через ТОТ ЖЕ generic-путь `get_match_affected_cells`,
    что и обычный сдвиг (в отличие от `cam`/`feedback`, у которых
    ОТДЕЛЬНЫЕ ветки с runtime-выбором exact-vs-conservative) — просто
    больший `reach`. Фикс работает на геометрии (`dist` vs `margin`/
    `safe_margin`), не на конкретном значении `reach` — plain-shift-тест
    уже подтверждает механизм для любого `reach`.
  - **`starvation_after`/`memory`/`max_activations`** — НЕ тестировались,
    осознанно: ни одно не меняет `get_match_affected_cells`'s вычисление
    клеток вообще (только `priority` через `resolve_sort_fields`, либо
    pre-arbitration гейтинг кандидатов) — не новый геометрический риск,
    какая бы форма сдвига/recursion/cam под ними ни была, уже покрыта
    остальными тестами.
  - Итог: ВСЕ различимые пути вычисления affected-региона (generic
    write_cells, CAM exact, feedback exact) проверены и защищены фиксом.
    Полный suite зелёный (254+23+13+11+2+2).

**Проверено и осознанно отклонено (с числами, чтобы не переизобретать):**

- **Vec+сортировка вместо `HashMap` для `write_buffer`** ("путь (а)") —
  реализовано полностью (`WriteSink`/`VecSink`, мономорфизация вместо
  `dyn`), но контролируемый A/B на реальном (не пред-отсортированном) CF
  показал регрессию **-19.9% до -104%** в зависимости от варианта — причина:
  обосновывающий микробенчмарк гонял на синтетических уже отсортированных
  данных, где сортировка искусственно дешева. Полностью откачено, комментарий
  с числами оставлен в коде. Прямая запись в решётку для safe-ветки ("путь
  в") отвергнута ещё раньше без реализации — граф конфликтов проверяет
  только write-write, не write-read, прямая запись могла бы читать чужие
  ещё не применённые записи.
- **Персистентность `regions`/`pending_boundary` в `apply_matches_with_cam`**
  — изолированно +19.3%, но это верхняя граница только для ВНЕШНЕГО `Vec`;
  доминирующая стоимость — во вложенном `written_cells: Vec` на каждый
  матч, который аллоцируется заново независимо от внешнего контейнера.
  Публичный контракт (`apply_matches` возвращает `Vec<AffectedRegion>` по
  значению) пришлось бы ломать `mem::take`+обратным присваиванием ради
  небольшого и неопределённого остатка выигрыша — не оправдано.
- **Рекурсивное деление boundary-полосы в `arbitrate_spatial_with_cam`** —
  измерение подтвердило реальную асимметрию (boundary — 32% матчей, но
  60-74% совокупного core+boundary времени на CA-пробке, сиквеншл на 1
  потоке против parallel на 24). Реализовано (рекурсивный вызов
  `arbitrate_spatial_with_cam` на `boundary`), математически корректно по
  Lemma 6 (10.7 специфики) — но на реальном прогоне **stack overflow**: в
  равномерно заполненной решётке новый boundary почти точно ложится на
  границы следующего уровня деления (резонанс между периодичностью
  паттерна и периодичностью самого band-split), множество не уменьшается.
  Полностью откачено, объясняющий комментарий оставлен в `arbitrator.rs`.
- **`boundaries: HashMap` → `FxHashMap`** в `Grid::set_cell` — не
  подтвердилось: `contains_key` на пустой карте (реальный случай для
  CF/CA) стоит одинаково что для SipHash, что для FxHash — обе схемы не
  доходят до полноценного хэширования на пустой карте.
- **SoA-раскладка решётки** (`Cell{value, born_at}` → раздельные массивы) —
  реальный, но не оправданный по объёму работы выигрыш: -25.7%
  изолированно на чтении соседей в detect, но требует переписать
  `GridStorage`, обе реализации (`VecStorage`/`ChunkStorage`) и весь
  публичный API доступа к клетке. Не реализовано, зафиксировано на случай,
  если решётка когда-нибудь станет узким местом номер один.
- **GPU+CPU async-пайплайнинг тиков** (перекрытие GPU-расчёта тика N+1 с
  CPU `cpu_fallback_resolve` тика N) — архитектурная задача сравнимого с
  VecSink-приключением риска и объёма, не пятиминутная проверка. Отложено
  без решения.

### Fixed — реентерабельность `KEYED_BUF` под нагрузкой (2026-08-11)

Найдено не в тестах, а при первом честном замере плотной производительности
на масштабе ~1M клеток (подготовка модели под проект городской симуляции):
`"RefCell already borrowed"` panic на 3-м тике из 5 на решётке 1000×1000.

- **Суть:** `KEYED_BUF.par_sort_unstable_by` (`arbitrator.rs`) вызывался
  ВНУТРИ заимствования `thread_local!`-буфера. rayon'овский work-stealing
  может увести ТОТ ЖЕ OS-поток на ДРУГОЙ вызов `arbitrate_with_cam`
  (соседняя полоса, тот же thread-local), пока первый ещё не вернулся из
  сортировки (ждёт свои подзадачи через `join`) — второй вызов пытается
  занять тот же `RefCell` и падает. Нужен per-полосный размер >=
  `PARALLEL_SORT_THRESHOLD=1024` — ни один тест до сегодняшнего замера
  такого не давал.
- **Фикс:** заимствование теперь берётся только на мгновенный
  `take`/возврат (`std::mem::take` + присваивание) — сама decorate/сортировка
  идёт на локальной переменной, без удержания `RefCell` во время
  параллельной сортировки. Та же персистентность (capacity сохраняется
  между вызовами), просто без риска.
- **Постоянный регрессионный тест** (дешёвый, не 1M клеток) —
  `tests/property_arbitration.rs::test_arbitrate_spatial_no_refcell_reentrancy_panic_with_many_matches_per_band`
  — много полос, каждая гарантированно > 1024 матчей, 5 прогонов подряд
  против timing-зависимости гонки. Сабо­таж-верифицирован — 3 из 3 попыток
  на исходном коде падали со100%-ной надёжностью (сама гонка воспроизводится
  стабильно, несмотря на timing-зависимую природу).
- `USED_CELLS_BUF`/`AFFECTED_BUF` тому же риску не подвержены — их область
  заимствования не содержит вложенных rayon-вызовов (проверено `grep`).
- **Замер плотной производительности на городском масштабе** (побочный,
  но ценный результат того же расследования, CA-сценарий, sequential CPU):
  90 000 клеток ≈26мс/тик, 360 000 ≈105мс/тик, 1 000 000 ≈408мс/тик —
  это ВСЕ клетки решётки активны одновременно (наихудший случай для
  плотности; реальный город вряд ли настолько плотен каждый тик). Полный
  suite зелёный (254+23+13+12+2+2).
- **Замер на реалистичной разрежённости и GPU** (та же 1000×1000 решётка,
  ~100 маленьких "пробок" 20×20, разбросанных по решётке — 3.8% активных
  клеток, остальное никогда не трогается):
  - CPU: ~10мс/тик в среднем, тёплые тики ~3-4мс — **~40x быстрее** 100%-
    плотного случая. Подтверждает: `grid.peek_dirty()`-based dirty-tracking
    реально держит обещание — стоимость тика пропорциональна АКТИВНОЙ
    области, не номинальному размеру решётки.
  - GPU (`GpuEngine`, тот же простой сдвиг, в подмножестве v2): тёплые
    тики **~1.3мс** на 3.8%-разреженной решётке, **~2.0-2.5мс** на 100%-
    плотной (1M клеток) — то есть **~180x быстрее CPU** на худшем случае
    (плотность GPU почти не задевает — параллелизм обрабатывает решётку
    целиком независимо от того, сколько реально активно, в отличие от
    CPU-шного dirty-tracking, которому разрежённость и выгодна).
    Первый(-ые) тик(и) — разовая стоимость компиляции шейдеров/инициализации
    (замечено: 3.3с и 495мс на первых двух тиках плотного случая, 30мс и
    20мс на разреженном) — не часть per-tick стоимости, платится один раз
    при создании `GpuEngine`, не каждый тик.
  - Итог для проекта городской симуляции: даже наихудший случай (100%
    плотность, 1M клеток) на GPU укладывается в ~400-500 тиков/сек —
    с большим запасом для реального времени. CPU-only тоже жизнеспособен
    при реалистичной (не 100%) плотности.

### Added — многослойная решётка (`LayeredEngine`, 2026-08-11)

Реализация парковавшегося ранее дизайна (см. запись ниже "Дизайн (без кода)
многослойной решётки"), в контексте подготовки модели под проект городской
симуляции: стек ОДИНАКОВЫХ по размеру 2D-слоёв (роли/домены — дороги,
здания, коммуникации, сенсоры — не геометрическая высота, то есть 2.5D, не
настоящее 3D). Первый срез — только ЧТЕНИЕ через слои, запись остаётся
намеренно нереализованной, отдельное более сложное расширение.

- `Rule::cross_layer_reads: Vec<(dx, dy, dz, CellType)>` — новое, полностью
  аддитивное поле (`#[serde(default)]`, `cross_layer_reads: Vec::new()` во
  всех 250+ существующих местах постройки `Rule` — сигнатуры `pattern`/
  `changes` не тронуты). `dz` индексирует СОСЕДНИЙ слой (не координату).
  Слои без `cross_layer_reads` между ними структурно НИКОГДА не
  конфликтуют по записи — арбитраж между разными слоями не нужен вообще,
  это верно по построению, а не для конкретного набора правил.
- `LayeredEngine<S>` (`src/layered.rs`) — стек НЕЗАВИСИМЫХ, немодифицированных
  `Engine`. Единственный новый механизм — фильтр между Detect и Arbitrate:
  кандидат с непустым `cross_layer_reads` отсеивается, если условие не
  выполнено на ПРЕДТИКОВОМ состоянии целевого слоя (та же дисциплина
  снимка тика 2.2.1, распространённая между слоями — сосед читается таким,
  каким он был на начало ЭТОГО тика, даже если сам поменяется позже в том
  же тике). `dz` за пределы стека или отрицательная координата — жёсткий
  отказ условия, не паника.
- `LayeredEngine::new` проверяет (`assert!`) все слои на одинаковый размер —
  без этого координата, валидная на одном слое, могла бы молча указывать
  на другую клетку (или вообще ни на какую) на другом слое внутри фильтра,
  без единой ошибки.
- `LayeredEngine::snapshot`/`from_snapshot` (`LayeredSnapshot<S>`) — снимок
  всего стека, по одному `EngineSnapshot` на слой; та же `serde_yaml`-
  дисциплина, что и у одиночного `Engine` (не `serde_json` — те же
  non-string ключи `HashMap`).
- `config::load_layered_config(paths: &[&str])` — грузит `LayeredEngine` из
  нескольких YAML-файлов (по одному на слой), каждый ровно тот же формат,
  что обычный `load_config` — никакого отдельного "многослойного" YAML-
  формата. Правила ВСЕХ файлов сливаются в один общий `rule_index`
  (слои структурно используют один набор правил), пересортированные по
  приоритету заново после слияния (конкатенация уже отсортированных
  кусков из разных файлов НЕ остаётся отсортированной сама по себе).
  Разноразмерные слои — понятная `CellariaError`, а не паника (внешние
  данные, в отличие от `LayeredEngine::new`, которому доверяет вызывающий
  программный код).
- Сознательно НЕ сделано в этом срезе (как и планировалось при дизайне):
  запись через слои (`changes`/`shifts` на другой слой), GPU-поддержка
  `LayeredEngine` — оба отдельные, более сложные расширения, не блокируют
  текущий срез.
- 10 новых тестов (6 `src/layered_tests.rs` + 4 `config.rs`), все
  сабо­таж-верифицированы: гейт реально гейтит (не no-op фильтр),
  дисциплина снимка тика через слои, `dz` вне стека не паникует,
  разноразмерные слои паникуют/возвращают ошибку по месту (программный
  конструктор vs YAML-загрузчик), snapshot/restore продолжает идентично
  (в т.ч. через cross-layer чтение), слияние правил из нескольких файлов
  пересортировано по приоритету, а не оставлено в порядке конкатенации.
- **Замер `LayeredEngine` на городском масштабе** (та же методология, что
  замер одиночного `Engine` выше — 300×300/600×600/1000×1000, 3 слоя,
  временный `#[ignore]`-тест, удалён после измерения):
  - Плотный худший случай (100% активных клеток на ВСЕХ 3 слоях
    одновременно): ~50-1270мс/тик в зависимости от размера (1000×1000×3
    слоя = 3М клеток ≈ 0.9-1.3с/тик) — растёт примерно линейно от числа
    слоёв, как и ожидалось (3 независимых `Engine` без общей работы между
    собой).
  - Реалистичная разрежённость (та же схема ~100 "пробок" 20×20 на
    1000×1000, ~4% активных, на всех 3 слоях): **~29-32мс/тик** — то же
    ~40x преимущество dirty-tracking, что и у одиночного `Engine`,
    сохраняется и через `LayeredEngine`, никакой отдельной деградации от
    самой обёртки не найдено.
  - Точную стоимость именно `cross_layer_reads`-фильтра (детект/арбитраж/
    apply слоя vs. добавленные point-lookups в соседний слой) этим
    замером выделить НЕ удалось — разброс между прогонами с фильтром и
    без него (~25-30%, в обе стороны при чередовании порядка измерений)
    больше, чем структурно может стоить сам фильтр (`cross_layer_reads`
    не читается НИГДЕ, кроме этого фильтра — ни детектом, ни арбитражем,
    ни кэшами правил, проверено `grep` по всей кодовой базе), то есть это
    шум незолированного замера на общей машине (единичный прогон на
    конфигурацию, не `criterion` со статистикой), а не реальный эффект.
    Если понадобится точная цифра именно этой добавки — нужен `criterion`-
    бенчмарк с повторами и отбросом выбросов, не сделан, не оправдан без
    конкретной нужды (сам фильтр по построению дешёвый — одна проверка
    `is_empty()` на несработавшем большинстве правил, O(число условий) на
    сработавшем меньшинстве).
  - **Вывод:** `LayeredEngine` GPU не поддерживает — при бюджете дорог/
    зданий/коммуникаций и т.п. как отдельных слоёв ПЛОТНЫЙ (не реалистично
    разрежённый) худший случай на CPU растёт линейно с числом слоёв и
    может стать реальным узким местом при большом числе слоёв. Для
    реалистичной разрежённости запаса по-прежнему много.

### Fixed — второй реальный баг в `arbitrate_spatial_with_cam` (2026-08-11)

Остаточный теоретический риск, задокументированный при фиксе ПЕРВОГО
boundary-vs-core бага (`specs/architecture.md` §11, п.5) — не гипотетика,

- **Суть:** финальный merge-проход (boundary + `at_risk`-победители полос)
  терял локальных проигравших. Три конкурента на клетку: L (слабый,
  проигрывает W в per-полосном арбитраже, отбрасывается НАВСЕГДА), W
  (побеждает L локально, но сам проигрывает B в финальном merge), B
  (boundary, выше приоритетом W, но НЕ пересекается с L). Централизованный
  арбитраж: B принят, W отклонён целиком (греди — не частично), L
  ПРОВЕРЯЕТСЯ НЕЗАВИСИМО (его клетка свободна — W её так и не забрал) — L
  принят. Spatial: L уже мёртв со стадии per-полосного раунда, никогда не
  участвует в merge — принят только B. Расхождение реальное.
- **Фикс:** в merge-проход теперь идут не победители per-полосного раунда,
  а ИСХОДНЫЕ кандидаты at-risk зоны целиком (`at_risk_zone_by_band`,
  собранные ДО первого арбитража, на этапе классификации) — и победители, и
  локально отклонённые. Per-полосный раунд остаётся ЕДИНСТВЕННЫМ источником
  `safe_accepted` (не меняется), но его решение для at-risk зоны полностью
  пересматривается в merge-проходе тем же тотальным порядком, что и
  централизованный арбитраж.
- **Побочная опасность, найденная и закрытая тем же фиксом:** at-risk зона
  физически МОЖЕТ пересекаться с safe-зоной той же полосы (несмотря на
  название) — at-risk-матч на границе своей зоны с `reach=K` может писать
  вплоть до `margin+K=safe_margin`, то есть на первую "safe" клетку. Слепое
  повторное участие локального проигравшего в merge-проходе могло бы дать
  ему повторно "выиграть" клетку, уже НАВСЕГДА занятую `safe_accepted` —
  двойная запись. Решено через новый опциональный параметр `reserved:
  &[(i32,i32)]` у `arbitrate_with_cam` (`&[]`, нулевая цена, для всех
  остальных вызовов) — `safe_accepted`'s клетки предзарезервированы в
  merge-проходе.
- **Верификация:** новый целенаправленный (не property, вручную
  сконструированный по аналитическому выводу) тест
  `test_arbitrate_spatial_matches_centralized_at_risk_loser_frees_locally_rejected_weaker_candidate`
  — сначала ПОЙМАЛ баг на неисправленном коде (не угадан, выведен из
  геометрии margin/safe_margin), затем подтвердил фикс. Сабо­таж-
  верифицировано дважды: убрать `at_risk_zone_by_band` → новый тест ловит;
  убрать `reserved` → уже ловят ТРИ существующих теста
  (`..._plain_shift_dense_overlapping_writes`,
  `..._recursion_dense_overlapping_writes`,
  `..._no_refcell_reentrancy_panic_...`) — отдельный тест на вторую
  опасность не понадобился. Полный suite зелёный (263 lib + 45 integration
  + 7 doc).
- **Замер производительности** (та же CA-"пробка" 300×300/600×600/1000×1000,
  сплошной сдвиг вправо, что и в записи про `mimalloc-alloc`/RefCell-фикс
  выше, временный `#[ignore]`-тест, удалён после измерения): 22.6/95.2/
  372.5мс/тик — в пределах шума от ранее записанных 26/105/408мс (тот же
  порядок, разница объясняется run-to-run вариацией железа, не
  регрессией). Дополнительная работа фикса (сбор `at_risk_zone_by_band` в
  ходе уже существующего классификационного прохода, `reserved_cells`

### Fixed / Added — `ChangeValue`: реальный баг сериализации + арифметика (2026-08-11)

- **РЕАЛЬНЫЙ БАГ:** `ChangeValue` был `#[serde(untagged)]` —
  `Literal(u8)`/`Ref(usize)` сериализуются НЕРАЗЛИЧИМО (оба голым числом).
  `Ref(3)` уходил в YAML как `"3\n"`, обратно приходил как `Literal(3)` —
  ЛЮБОЕ правило с `Ref` в `changes`, пройдя через
  `Engine::snapshot()`/`from_snapshot()` (или `replay()`, тоже идущий через
  снимок), тихо теряло смысл: вместо "скопировать значение из паттерна"
  начинало писать литерал, равный индексу ссылки. Найдено эмпирически при
  подготовке модели к 1.0 (не угадано) — ни один property/snapshot-тест
  этой сессии не строил `changes` с `Ref` ради проверки через снимок,
  поэтому не ловилось никогда раньше. Убрано `#[serde(untagged)]` — YAML-
  конфиги не затронуты (`config::parse_change_value` парсит `changes`
  вручную из `serde_yaml::Value`, не через derive `Deserialize` этого
  enum — тегирование касается ТОЛЬКО внутренней сериализации снимков).
  Сабо­таж-верифицировано (вернуть `#[serde(untagged)]` → новый тест
  `test_change_value_ref_survives_serde_roundtrip_and_snapshot_restore`
  немедленно ловит, воспроизводя баг один-в-один).
- **Добавлено — `ChangeValue::Add`/`Sub`:** рекурсивная арифметика
  (операнды сами `ChangeValue` — числа, `Ref`, или вложенные `Add`/`Sub`),
  `u8::wrapping_add`/`wrapping_sub`. YAML: `{add: [a, b]}`/`{sub: [a, b]}`,
  например `{add: ["$0", 1]}`. Единственный пробел из списка "что явно
  понадобится дочерним проектам" (счётчики/пороги/накопление ресурсов),
  названный при планировании 1.0.
  - **CPU:** полная поддержка, произвольная глубина вложенности.
  - **GPU:** явно НЕ поддерживается (`GpuUnsupportedReason::ChangeIsArithmetic`,
    та же категория, что уже была у `ChangeValue::Ref`) — правило целиком
    уходит в CPU-fallback, не тихо считает неправильно.
  - **Протокол самомодификации:** явно НЕ кодируется — `push_change`
    возвращает `Err`, НЕ тихо пропускает (в отличие от `feedback`/
    `memory`/`keep_source`, которые вообще нигде не имеют байта/бита и
    потому просто отсутствуют в пакете целиком: `changes` же УЖЕ активно
    кодируется поэлементно, так что тихий пропуск ОДНОЙ записи означал бы
    тихую потерю данных для конкретной клетки, а не документированное
    "правило целиком не может нести это расширение").
  - **Честно задокументированное структурное ограничение:** `CellType` —
    одновременно значение (что арифметика читает/пишет) И ключ матчинга
    (`Rule::id`/`pattern` матчат ТОЧНЫЙ тип) — "счётчик, растущий на 1
    каждый тик ОДНИМ правилом" не выражается напрямую: после первого
    применения клетка становится другим `CellType`, исходное правило на
    него больше не сработает. Тест
    `test_change_value_add_applies_once_from_pattern_ref` демонстрирует
    это явно (второй тик, значение не меняется), а не прячет.
  - 12 новых тестов (парсинг YAML — плоский/вложенный/ошибки, конец-в-конец
    через `Engine` — однократное применение/wrapping-переполнение/

    debug-режим с overflow-checks (wrapping-арифметика не паникует).

## [0.6.0] - GPU backend & model extensions

Два независимых, но параллельно шедших направления: опциональный GPU-бэкэнд
(`wgpu`, feature `gpu`) как второй исполнитель тика рядом с CPU `Engine`, и
пять новых, самостоятельно доказанных расширений модели — плюс закрытие
четырёх ранее открытых вопросов (три оказались уже корректно решены и
получили тесты/доказательство, один потребовал новый пример).

### Added — GPU-бэкэнд (feature `gpu`)

- `gpu::GpuEngine` — второй, необязательный исполнитель тика поверх `wgpu`
  compute-шейдеров, побитово (включая `born_at`) сверенный с CPU `Engine` на
  каждом тике, а не только "в среднем" (`tests/gpu_v1_correctness.rs`,
  `tests/gpu_v2_correctness.rs`).
- Два пайплайна, выбираемые автоматически по форме конфига
  (`GpuRuleTable::needs_arbitration`): `main` — однопроходный self-write-only
  путь (например, Game of Life: каждый поток пишет только свою клетку, конфликтов
  в принципе нет); `detect_pass → claim_pass/resolve_pass (×ROUNDS) →
  count_pending → apply_pass` — многораундовый lock-free арбитраж для
  сдвигов и записи в соседа, с тем же тотальным тай-брейком
  (`priority → age → tie_break → id → x → y → rule_idx`), что и CPU
  `arbitrator::arbitrate`. Число раундов до сходимости растёт линейно с
  длиной цепочки зависимых конфликтов — несошедшиеся за `ROUNDS` матчи
  досчитываются на CPU (`GpuEngine`'s гибридная схема), не отбрасываются.
- `Rule::cam` (content-addressable поиск с ограниченным радиусом) — полностью
  на GPU: `cam_search` в шейдере зеркалит CPU `search_nearest` (тот же
  тай-брейк по расстоянию/позиции), радиус ограничен `MAX_CAM_RADIUS=16`
  (иначе `GpuUnsupportedReason::CamRadiusTooFar`).
- Явный, а не молчаливый отказ строить `GpuRuleTable` для того, что GPU-путь
  не может воспроизвести побитово: `ChangeValue::Ref`, `OverflowAction::Write`/
  `WriteLiteral` на сдвиге, `ShiftSpec::broadcast`, `Rule::starvation_after`,
  и ряд структурных потолков (длина id/паттерна, число сдвигов/changes,
  величина сдвига) — весь конфиг целиком отказывается собираться в GPU-таблицу,
  а не тихо теряет часть правил.
- `examples/flagship_gol.rs`/`flagship_shifts.rs` — сравнение CPU/GPU (и,
  где применимо, наивной Rust-реализации) на self-write-only и сдвиговой
  нагрузке соответственно.

### Added — новые возможности модели

- `Rule::cam` (CPU) — content-addressable "магнит": ищет ближайшую клетку
  заданного типа в радиусе (Chebyshev-диск), не только через явный `pattern`.
  Статически ограниченный радиус сохраняет решаемость графа конфликтов
  (диск — консервативная, но конечная граница), точная найденная позиция
  используется только на этапе арбитража конкретного тика.
- `ShiftSpec::broadcast` — вариант сдвига, заполняющий копией значения ВЕСЬ
  путь сдвига, а не только конечную точку (исходная клетка по-прежнему
  очищается — данные перемещаются с размножением по пути, не клонируются).
  CPU-only, GPU явно отказывается (шейдер пишет только финальную точку).
- `Rule::tie_break` — опциональный модульный тай-брейк между совпадениями с
  РАВНЫМ priority и возрастом: `(tie_break + generation) % 16`. При
  значении 0 у всех правил не меняет старое поведение (падает на
  лексикографический порядок `id`); при разных значениях победитель
  чередуется по тикам, а не фиксирован навсегда — решает голодание при
  равном приоритете. Полная CPU+GPU-параллель (шейдер, `GpuMatchLayout`,
  CPU-side hybrid-fallback компаратор — все три места синхронизированы).
- `Rule::starvation_after` — опциональная защита от голодания при РАЗНОМ
  приоритете (`tie_break` эту ситуацию не решает: priority сравнивается
  первым и решающим образом). Если конкретный матч `(x, y, rule_idx)`
  проигрывает арбитраж `K` тиков подряд — на `(K+1)`-й его эффективный
  priority становится максимальным (гарантированная разовая победа), дальше
  счётчик сбрасывается. Персистентное состояние живёт в
  `Engine::starvation_counters`, доступно только через `Engine::run_tick`
  (не через свободную функцию `run_tick`, как и CAM/самомодификация).
  CPU-only — GPU явно отказывается (`StarvationGuardUnsupported`): фича
  требует состояния МЕЖДУ тиками, которого GPU-путь принципиально не хранит.
- Конструктивные доказательства (без единой правки движка, кроме перечисленного
  выше): TMR/кворумный арбитраж (`proof_quorum_fault_tolerance.rs`) — три
  реплики + внешнее голосование, опирается только на уже доказанный
  детерминизм; PRNG из обычных правил (`proof_prng_from_rules.rs`, Rule 30);
  PRNG реально выбирает направление в правиле, которое решётка сама себе
  устанавливает через `RuleStore` (`proof_prng_driven_self_modification.rs`);
  внешняя фитнес-селекция среди N само-мутировавших реплик
  (`proof_evolutionary_fitness_selection.rs`); автономная самопроверка без
  внешнего наблюдателя — сравнение двух тактируемых счётчиков ОБЫЧНЫМ
  правилом, не внешним кодом (`proof_autonomous_self_verification.rs`).
- Дизайн (без кода) многослойной решётки (стек 2D-слоёв, не настоящее 3D) —
  задокументирован для значительно более позднего этапа.

### Fixed / Resolved — ранее открытые вопросы

- Доказательство обратимости (`proof_reversibility.rs`) не касалось выхода

внутренних hot-path структур осталась на стандартном `HashMap`/`HashSet`

собственного бенчмарк-набора проекта меряла не то, что заявлено.

### Fixed

- Три из семи сценариев "Фаза 1: Максимальный throughput" в
  `benches/throughput.rs` фактически не измеряли устойчивый throughput:
  - **1A** (`setup_no_shift`): правило `1,2→3,4` без обратного — решётка
    конвертируется целиком на ПЕРВОМ тике, для типов 3/4 правил нет, и
    все последующие тики в измерительном окне (100ms) пустые. Метрика
    "tps" была фактически "N² / длина окна", а не "тиков в секунду" — росла
    с N почти линейно независимо от реальной скорости движка. Тот же
    паттерн уже был найден и исправлен для 1E (см. её собственный
    doc-комментарий в коде), просто не перенесён на 1A при добавлении.
    Исправлено тем же способом: двухтактный осциллятор `1,2⇄3,4`.
  - **1C** (`priority_conflict_rules`, M конфликтующих правил на одной
    ячейке): побеждает ровно одно правило (наивысший приоритет) на первом
    тике, дальше клетка навсегда другого типа, для которого правил нет.
    Симптом был откровенным: `tps` был практически ОДИНАКОВ для M=10, 50,
    100, 200 — то есть число конкурирующих правил вообще не влияло на
    результат. Добавлено возвратное правило от типа-победителя обратно к
    типу 1 — теперь M-конфликт и настоящий арбитраж происходят на каждом
    "прямом" такте. После фикса `tps` корректно падает с ростом M (167k →
    47k → 24k → 12k для M=10/50/100/200) — конфликт-разрешение действительно
    стоит тем дороже, чем больше претендентов.
  - **1B/1F** (`setup_with_shift`, TM-подобная лента из N независимых
    сдвиговых правил): не мгновенная смерть, как 1A/1C, но та же причина —
    решётка была `VecStorage` фиксированной ширины `n+2`, движущиеся клетки
    неизбежно доходят до правого края и теряются
    (`OverflowAction::Discard` по умолчанию); при N=100 последнее реальное
    совпадение — на тике ~136, дальше окно бенчмарка (тысячи тиков) снова
    измеряет по большей части пустоту. Заменили хранилище на `ChunkStorage`
    (без края) — активность подтверждена сохраняющейся 2000+ тиков подряд.
- FxHash-миграция v0.6.0 покрыла не все внутренние hot-path структуры:
  - `Grid::active_index`/`Grid::dirty_coords` — задеваются КАЖДЫМ
    `set_cell`, единственной точкой мутации клетки в кодовой базе. Замерено
    на плотном осцилляторе (N×N шахматка): на 19-36% быстрее в зависимости
    от N (эффект растёт с размером решётки).
  - `ChunkStorage::chunks` — задевается каждым `get`/`set` на безграничной
    решётке. Замерено (много раздельных регионов, как в `big_world.rs`):
    на 25-30% быстрее.
  - `matcher::GroupData::offset_map`/`exact_lookup` и `GroupCache` —
    внутренности САМОЙ оптимизации из v0.6.0 (точный hash-lookup паттернов
    для смешанных групп) всё ещё работали на `SipHash`, частично гася
    собственный выигрыш. Замерено (голова с N точных правил + 1 wildcard):
    на N=2000 суммарный эффект обоих фиксов (v0.6.0 + это) — почти в 4.4
    раза быстрее исходной (до v0.6.0) версии, а не ~2 раза, как только от
    первого фикса.
  - Не тронуто сознательно: `BoundaryBuffer::queues`,
    `RuleStore::accum_buffers`, `Grid::boundaries` — либо публичный API
    (смена хешера — breaking change типа), либо не горячий путь (задеваются
    только во время активной самомодификации/IO, не каждый тик).

## [0.6.0] - performance hardening

Продолжение проверки производительности после v0.5.0: искали, почему одно
"движущееся" правило (челнок в `big_world.rs`) стоит на порядок дороже
статичного — и по ходу нашли четыре независимых места, где движок либо был
без нужды консервативен, либо пересчитывал что-то заново каждый тик, хотя
могло бы быть посчитано один раз.

### Fixed

- `ConflictGraph`: правило со сдвигом и `OverflowAction::Write`/`WriteLiteral`
  форсированно считалось потенциально конфликтующим с ЛЮБЫМ другим пишущим
  правилом — теперь только если клэмпинг на границе решётки НЕ доказуемо
  безопасен. Добавлены `ConflictGraph::build_with_grid`/
  `check_composition_with_grid` + `GridContext`: если весь край решётки в
  направлении сдвига покрыт настроенными `BoundaryBuffer` (доказуемо не
  задевает саму решётку, только изолированную очередь), такое правило больше
  не форсируется. Копнули глубже: для guarded self-modification с реальными
  физическими носителями это НЕ решает проблему целиком — там другая,
  более фундаментальная причина (см. "Changed" ниже) — но сам фикс
  корректен и общеполезен для обычных отскоков от границ решётки.
- Обход арбитража (`Engine::safe_heads` → удалено): голова была БЕЗУСЛОВНО
  и НАВСЕГДА помечена "небезопасной", если хоть с одной другой головой во
  ВСЁМ наборе правил структурно могла столкнуться — независимо от того,
  встречались ли они когда-либо на решётке. Одно движущееся правило
  (челнок, за миллион клеток от провода и распада в `big_world.rs`) гасило
  быстрый путь для ВСЕХ 7 голов сразу, включая 5 статичных, физически
  никогда с ним не соприкасающихся. Заменено на `Engine::conflict_partners`
  (та же структурная информация) + `spatial_bypass_split`: решение
  принимается КАЖДЫЙ тик заново, по реальным позициям совпадений — голова
  безопасна В ЭТОМ тике, если ни один её структурный партнёр не совпал в
  пределах `2 × max_affected_radius`. Проверено: провод и распад в
  `big_world.rs` теперь проходят без арбитража каждый тик независимо от
  челнока; итоговая стоимость связки — сумма частей, без штрафа за
  сосуществование.
- Матчер: `GroupData::exact_lookup` (O(1) hash-lookup паттернов вместо
  перебора) отключался для ВСЕЙ группы правил головы, если хоть ОДНО
  правило группы было wildcard (не читало часть соседей) — даже когда
  остальные правила той же головы были полностью специфицированы. Теперь
  `exact_lookup` строится по подмножеству полностью специфицированных
  правил, `fallback_rules` — только оставшиеся wildcard-правила.
  Замерено (голова с N точных правил + 1 wildcard, до/после): N=10 — не
  отличимо от шума; N=500 — на 35% быстрее; N=2000 — больше чем в 2 раза
  быстрее. Для голов с 1-2 правилами (как у челнока) эффект несущественный —
  экономить почти не на чем.
- `min_age_gated_types`/`max_pattern_radius`/`zero_head_radius` — чистые
  функции только от `rule_index`, но пересчитывались заново на КАЖДЫЙ тик
  (внутри `resolve_search_coords_advance`/`_peek`), хотя не меняются, пока
  не меняются сами правила. При 1000 независимых голов в наборе — рост с
  ~24 нс/тик до ~1950 нс/тик просто на этом пересчёте, безотносительно
  реальной работы. Вынесены в `Engine::search_radius_cache`, считаются один
  раз при создании/`rebuild_rule_cache` — после фикса стоимость не растёт с
  числом голов вообще (замерено: плоские ~24 нс/тик что при 10, что при
  1000 головах).

### Changed

- Найдена и не признана багом: guarded self-modification в принципе
  несовместим с физическими носителями (клетками, реально движущимися по
  решётке для доставки байт протокола) — не из-за клэмпинга на границе
  (см. "Fixed" выше), а потому что позиционно-независимый анализ
  конфликтов не может исключить, что клетка-носитель когда-нибудь окажется
  физически рядом с только что установленным правилом. Единственный
  рабочий способ — прямая инъекция байт в очередь (уже задокументирован в
  `proof_guarded_self_modification.rs`), а не транспорт через движущиеся
  клетки-курьеры.

## [0.5.0] - closed-loop self-modification

Сравнение с `v0.3.0: 2D patterns` (`d0af206`) — включает также локальный
коммит `tests and configs` (0.4.0, ниже) и всё, что описано в этом разделе.

### Added

- Протокол самомодификации (`RuleStore`) полностью подключён к
  `Engine::run_tick`: решётка сама выталкивает байты пакета
  `AddRule`/`RemoveRule`/`ClearAll` через выходной граничный порт, движок сам
  их собирает, декодирует и применяет к своему `rule_index` — без единого
  внешнего вызова между тиками (`Engine::enable_self_modification`).
- `Engine::enable_guarded_self_modification` — самопереданное правило
  проверяется уже доказанной теоремой композиции
  (`ConflictGraph::check_composition`) перед установкой и отклоняется, если
  доказуемо конфликтует с "защищённым" набором — правилами, существовавшими
  до включения самомодификации.
- Обход арбитража для голов, доказанно не участвующих ни в одном ребре графа
  конфликтов (`Engine::safe_heads`, Theorem 3 "Arbitration Bypass",
  paper2.md §3.7) — их матчи принимаются напрямую, без единого сравнения.
- Инкрементальный `detect_matches`: `Grid` отслеживает "грязные" координаты
  (`dirty_coords`/`take_dirty`/`mark_dirty`), и следующий скан ограничивается
  окрестностью реально изменившихся с прошлого тика клеток, а не всеми
  активными.
- Точный hash-lookup паттернов (`GroupData::exact_lookup`) для групп правил,
  где каждое правило полностью специфицирует все смещения без wildcard —
  вместо линейного перебора (для Game of Life — до 172 правил на голову).
- Упаковка паттернов расширена с u64 (≤8 клеток) до u128 (≤16 клеток) —
  паттерны вроде Game of Life (9 клеток: центр + соседи) тоже попадают в
  быстрый путь.
- `OverflowAction::WriteLiteral` — в отличие от `Write`, байт `0` не имеет
  специального смысла "пронести собственное значение головки"; нужен, чтобы
  протокол самомодификации мог передавать байт со значением 0.
- `src/fast_hash.rs` (`FxHash`) вместо `SipHash` для внутренних hot-path
  структур (координаты клеток, типы правил) — входные данные не из
  недоверенного источника, устойчивость к преднамеренным коллизиям не нужна,
  а скорость на мелких ключах — нужна.
- `examples/showcase_self_governing_world.rs` и полный набор
  `proof_*`/`strength_*` демо — конструктивное доказательство каждого
  свойства (самомодификация, охраняемая композиция, самоаттестация,
  обратимость, распространение сбоя) отдельным исполняемым примером.

### Fixed

Пять багов, найденные целенаправленным ревью самомодификации (все с
regression-тестами, см. paper2.md §4.6):

- `RemoveRule` не убирал голову из `rule_index`, если после удаления
  сторонних правил для неё не оставалось.
- Самопереданное правило, расширяющее уже существующую голову, стирало
  исходное правило вместо добавления к нему — `RuleStore::get_index()`
  ничего не знает о правилах, установленных вне протокола.
- Снимок "защищённых" правил (`original_rule_index`) брался только в момент
  `Engine::new` и не учитывал правило, добавленное после конструирования, но
  до `enable_self_modification`.
- Несколько независимых выходных портов делили один буфер декодирования
  (`accum_buffers`, ключ по каналу, а не по границе) — параллельная передача
  с двух портов перемешивала байты в один повреждённый поток.
- Guard проверял кандидата против `rule_index`, обновляемого только в конце
  тика, а не против уже принятых в ЭТОМ ЖЕ тике операций — два конфликтующих
  самопереданных правила, завершившихся в одном тике, проходили оба.

Отдельно, найдено попутно (не в самомодификации):

- `set_cell` решал "вставить/убрать из `active_coords`" по пересчитанному
  `is_default()` предыдущей ячейки, а не по фактическому членству в кэше —
  ломалось после `reset_age_for_regions` (обновляет `born_at` в обход
  `set_cell`); клетка могла навсегда выпасть из `active_coords`.
- Сброс возраста после применения матчей использовал bounding box затронутой
  области (`AffectedRegion`), а не точный список реально записанных клеток —
  клетка внутри bbox, но не тронутая ни одной записью (например, между
  исходной и целевой позицией сдвига на N>1), получала обнулённый возраст,
  хотя не менялась. Добавлено `AffectedRegion::written_cells`.
- `RuleMatch.rule_id: Vec<CellType>` клонировался на каждое совпадение (сотни
  тысяч аллокаций за тик на плотных решётках) — заменён на `Copy`-поле
  `head: CellType`; полный `id`, если нужен, восстановим через
  `rule_index[head][rule_idx].id`.

### Changed

- `ConflictGraph` теперь различает клетки, которые правило ЧИТАЕТ, от клеток,
  которые оно реально ПИШЕТ (`RuleData::write_cells`) — конфликт по
  пересечению записей, а не чтений; убирает часть ложных срабатываний для
  обычных (не выходящих за границу решётки) сдвиговых правил. Известное
  ограничение осталось: правило со сдвигом и `OverflowAction::Write`/
  `WriteLiteral` по-прежнему форсированно считается потенциально
  конфликтующим с ЛЮБЫМ другим пишущим правилом (клэмпинг на границе
  решётки непроверяем без знания её размера) — для протокола
  самомодификации, чьи носители байт как раз такие, конфликты по-прежнему
  завышаются; guarded self-modification там всё ещё требует прямой инъекции
  байт в очередь вместо честной передачи через физические носители.
- `GroupData` (матчер) больше не хранит `&[Rule]`, только скопированные
  `(min_age, active_only)` — убирает время жизни, что позволило `Engine`
  кэшировать `GroupCache` между тиками вместо пересборки на каждый.

## [0.4.0] - tests and configs

Сравнение с последней версией на GitHub на тот момент (`v0.3.0: 2D patterns`,
`d0af206`). Коммит `tests and configs` не был помечен тегом.

### Fixed

Баги, найденные ревью кода и property-based фаззингом (`proptest`), с regression-тестами:

- `Cell.age` переименован в `born_at`: возраст теперь вычисляется как
  `generation - born_at` (глобальный счётчик поколений в `Grid`), а не хранится
  и не продвигается на каждой ячейке — заодно делает `advance_age` операцией
  O(1) вместо обхода всех ячеек.
- `RuleMatch` получил поле `rule_idx` — несколько правил могут иметь одинаковый
  `id` (недетерминированный выбор), и без `rule_idx` арбитраж/применение могли
  резолвиться не к тому правилу, которое реально сработало.
- Тай-брейк в `arbitrate()` сделан полностью явным:
  `priority → age → rule_id → x → y → rule_idx` (раньше при равенстве
  priority+age порядок был implementation-defined) — гарантирует идентичный
  результат между глобальным последовательным и локальным раундовым
  арбитражем.
- `ConflictGraph::build` теперь проверяет правило на конфликт с самим собой
  (`rule_self_conflicts`) — раньше правило, конфликтующее само с собой в двух
  перекрывающихся позициях, не обнаруживалось, что нарушало теорему
  «бесконфликтность ⇒ арбитраж не нужен».
- `arbitrate()` больше не отбрасывает affected cells с отрицательными
  координатами из проверки конфликтов (раньше guard `>= 0` пропускал такие
  ячейки мимо `used_cells`, позволяя двум пересекающимся в отрицательных
  координатах матчам пройти арбитраж вместе).
- Клэмпинг affected cells при `OverflowAction::Write` теперь учитывается в
  анализе конфликтов согласованно с реальной (клэмпнутой) позицией записи,
  а не с отброшенной абстрактной координатой.
- Правила с 2+ независимыми сдвигами (`ShiftSpec`) теперь применяют `changes`
  один раз на каждую реальную цель сдвига (`shift_targets`), а не один раз на
  их сумму (`total_shift`) — раньше изменения попадали в точку, не
  совпадающую ни с одной реальной целью записи.
- Кэш `active_coords` в `Grid` переведён с `HashSet` + полная пересборка `Vec`
  на `Vec` + индекс `HashMap` со `swap_remove` — удаление теперь O(1)
  амортизированно вместо O(число активных ячеек) (раньше каждый сдвиг головки,
  всегда очищающий исходную позицию, стоил O(A)).

### Changed

- **Бенчмарки** (`benches/`) переписаны: `Criterion`-тесты теперь делают
  setup один раз и замеряют один тик на семпл, а не оборачивают
  самостоятельно-таймингующие циклы внутри `b.iter()`; флаг кастомного
  репортера переименован `--bench` → `--criterion` (Cargo сам всегда
  дописывает `--bench` в argv, что делало кастомный путь недостижимым);
  направление регрессии от baseline исправлено для throughput-метрик
  (раньше рост throughput ложно помечался предупреждением, а падение не
  ловилось); `--output` теперь сохраняет результат даже вместе с
  `--json`/`--quiet`/`--compact`.
- Удалён неиспользуемый вариант `BenchStatus::Fail` из репортера бенчмарков
  (нигде не создавался — не было конструктора `.fail()`, только `.pass()`/`.peak()`).
- Крупные инлайн-блоки `#[cfg(test)] mod tests { ... }` вынесены в соседние
  файлы (`engine/tests.rs`, `conflict_analyzer_tests.rs`, `tm_translator_tests.rs`,
  `rule_store_tests.rs`, `storage_tests.rs`) — чисто структурная правка,
  поведение не меняется.
- `test_config.yaml` перемещён в `configs/`.
