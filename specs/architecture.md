# Архитектура (внутреннее устройство)

Этот документ — **не история изменений** (для этого CHANGELOG.md) и **не
модель** (для этого [specification.md](specification.md) — аксиомы,
формальная семантика, доказательства). Здесь — **текущее** устройство
реализации: как код внутри устроен и почему именно так, а не иначе.
Поддерживается в актуальном состоянии; при архитектурных изменениях
правится ЭТОТ файл, а не только CHANGELOG.

## 2. Тик-пайплайн

`Engine::run_tick()` → `run_tick_with_cache()` (`engine/mod.rs`), пять фаз:

1. **Input** — НЕ автоматическая часть тика. `push_input()` кладёт значение
   в очередь буфера; перенос очереди на граничную ячейку делает отдельный,
   явно вызываемый `apply_input()`. Канонический паттерн вызывающего кода:
   `apply_input()` каждый тик безусловно, ДО `run_tick()`.
2. **Detect** (`matcher.rs`) — поиск совпадений по всей решётке (или
   инкрементально по dirty-множеству), читает **только pre-tick** состояние
   решётки (дисциплина снимка тика, специф. §2.2.1). Параллелится через
   rayon выше `matcher::PARALLEL_THRESHOLD`.
3. **Arbitrate** (`arbitrator.rs`) — жадный алгоритм по детерминированному
   ключу сортировки (специф. §7); см. §5 ниже про пространственное
   разбиение на полосы.
4. **Apply** (`applicator.rs`) — запись изменений принятых матчей в буфер,
   один flush в решётку. `Rule::recursion` — единственное отступление от
   "detect читает только pre-tick": каскад читает уже накопленный этим же
   каскадом буфер (специф. §4.7).
5. **Flush** — единый проход `write_buffer` → `grid.set_cell()`, чистка
   `pattern_buffer`.

`spatial_bypass_split` (`engine/mod.rs`, вызывается КАЖДЫЙ тик) делит
совпадения на `safe` (арбитраж пропускается — см. специф. §10.7) и
`unsafe_matches` (идут в полный арбитраж) ДО фазы Arbitrate — это не
отдельная фаза, а предварительный фильтр внутри неё.

## 3. Персистентное состояние правил — `RuleStateStore`

`engine/rule_state.rs`. Единая точка хранения `starvation_counters`/
`feedback_counters`/`memory_buffers`/`activation_counters` +
`last_rebuilt_rule_index` (снимок для чистки осиротевших записей).

**Почему не четыре отдельных поля на `Engine` (как было раньше):**
дисциплина снимка тика (Detect/Arbitrate обязаны видеть эти карты КАК ОНИ
БЫЛИ на начало тика, запись — только после) раньше держалась ТОЛЬКО
соглашением программиста — простые `&mut FxHashMap` ничем не мешали
прочитать уже обновлённое в этом же тике значение. Именно так родился
реальный баг с `feedback_counters` (инкремент стоял МЕЖДУ чтением при
арбитраже и чтением при apply — см. CHANGELOG, `[0.7.0] / Fixed`).

**Как это закреплено в типах, а не в ревью:**
- `snapshot() -> RuleStateSnapshot<'_>` — держит `&RuleStateStore`
  (разделяемое заимствование), для Detect/Arbitrate.
- `mutate() -> RuleStateWriter<'_>` — держит `&mut RuleStateStore`
  (эксклюзивное), для пост-арбитражных обновлений.
- Borrow checker физически не даёт получить `mutate()`, пока где-то ещё жив
  `snapshot()` — ошибка компиляции, не баг в рантайме.

**Единственное осознанное исключение:** `applicator::apply_rule_buffered`
("Фаза 1") для ПОБЕДИВШЕГО матча с `Rule::feedback` — чтение счётчика (для
`feedback_override`) и его инкремент обязаны быть атомарной операцией ДО
релокации записи при сдвиге; разделять на снимок+писателя было бы опаснее
(легко забыть релоцировать после инкремента отдельным проходом). Единственное
место, где чтение идёт через `RuleStateWriter` целиком.

**Ключи состояний** (все в `arbitrator.rs`, рядом с типами):
| Состояние | Ключ | Почему |
|---|---|---|
| `StarvationCounters`, `FeedbackCounters`, `MemoryBuffers` | `(x, y, rule_idx)` | привязаны к позиции матча, переносятся при сдвиге (`apply_shift_buffered`) |
| `ActivationCounters` (`max_activations`) | `(head, rule_idx)` | ГЛОБАЛЬНЫЙ бюджет правила, не позиции — перенос не нужен |

## 4. Расширения модели: сводка

| Расширение | Поле `Rule`/`ShiftSpec` | Межтиковое состояние | CPU | GPU |
|---|---|---|---|---|
| CAM (притяжение к типу) | `Rule::cam` | нет (пересчитывается каждый тик) | да | да |
| Голодание | `starvation_after` | `StarvationCounters` | да | да |
| Каскад в тике | `recursion` | нет | да | да (`MAX_RECURSION_DEPTH=4`) |
| Защёлка направления | `feedback` | `FeedbackCounters` | да | да |
| FIFO-гейт по истории | `memory` | `MemoryBuffers` | да | да (оба триггера) |
| Излучение (не очищает источник) | `keep_source` | нет | да | **нет** (`KeepSourceUnsupported`) |
| Глобальный бюджет побед | `max_activations` | `ActivationCounters` | да | **нет**, явно отвергается при построении GPU-таблицы (`rule_table.rs:747`, `GpuUnsupportedReason`) |

Комбинации, структурно исключённые (не "не реализовано", а нет
определения): `memory(RuleOutcome)` + `recursion` (у уровня каскада нет
отдельного шага арбитража — "выиграл/проиграл" не определено). Комбинации/
поля, исключённые только на GPU (реализуемы на CPU): `cam`+`recursion`,
`memory`+`recursion`, `memory`+`cam`, `feedback`/`memory`+`broadcast`,
`feedback`/`memory`+`changes` на том же смещении, что цель сдвига,
`max_activations`, `keep_source` — см. `gpu/rule_table.rs::GpuUnsupportedReason`
и специф. §13.4 (таблица).

## 5. Пространственное разбиение арбитража

`arbitrate_spatial_with_cam` (`arbitrator.rs`) — при большом числе матчей
делит решётку на **полосы** по x-координате (столько полос, сколько rayon
потоков, но не уже удвоенного margin `2 × reach`). Каждая полоса —
`core` (совпадения дальше `margin` от ОБЕИХ границ полосы, арбитрируются
параллельно, Lemma 6 специф. — разные полосы никогда не делят клетки) +
`boundary` (совпадения ближе `margin` к какой-либо границе).

**РЕАЛЬНЫЙ БАГ, найден и исправлен 2026-08-10** (не гипотетический —
воспроизведён на реальном коде до фикса): раньше `core` и `boundary`
арбитрировались ПОЛНОСТЬЮ НЕЗАВИСИМО (boundary — сам с собой, последовательно)
и их результаты просто СКЛЕИВАЛИСЬ, без единой перекрёстной проверки.
`margin = 2×reach` (Lemma 6) доказывает только "core-матчи из РАЗНЫХ полос
не пересекаются" — про boundary-против-соседнего-core (в том числе того же
самого band'а!) теорема ничего не говорит и не может: boundary-матч прямо
на границе своей зоны (`dist = margin-1`) физически может писать ещё на
`reach` клеток дальше, вглубь соседней core-зоны (которая начинается сразу
на `dist = margin`) — конструктивно доказано, что НИ ОДИН конечный margin
с простой пороговой схемой (`dist >= margin ⟹ core`) не может это исключить
в общем случае, для любого `reach >= 1`. Никогда не ловилось раньше, потому
что все существовавшие Lemma-6-тесты использовали правила с записью в ОДНУ
точку (без сдвигов, без `recursion`) — точка не может дотянуться через
границу вне зависимости от margin; `recursion` (сессия 2026-08-10) стало
первым правилом в истории тестов проекта с реальной многоклеточной записью,
прогнанным на масштабе, где boundary-путь вообще включается
(`SPATIAL_THRESHOLD=4096`), и немедленно обнажило проблему. Конкретный
репро остался тестом:
`tests/property_arbitration.rs::test_arbitrate_spatial_matches_centralized_recursion_dense_overlapping_writes`.

**Серьёзность выше, чем казалось первоначально:** проверено отдельно
(`test_arbitrate_spatial_matches_centralized_plain_shift_dense_overlapping_writes`)
— баг ловится и на ОБЫЧНОМ одиночном сдвиге (без `recursion`, без `cam`),
самом частом случае в принципе. Значит CA-"пробка" (сплошной сдвиг вправо,
300×300), которую эта сессия гоняла весь день ради замеров
производительности (`Engine::run_tick_profiled`, ~44000+ принятых матчей
за тик — далеко за `SPATIAL_THRESHOLD=4096`), могла ВСЁ ЭТО ВРЕМЯ тихо
принимать конфликтующие записи — сверялось только время, не содержимое
решётки. Баг не специфичен для `recursion`/`cam` — фундаментальная
проблема самого алгоритма band-split, задевающая любой конфиг с
достаточно плотной конкуренцией на любом `reach >= 1`. `recursion` просто
оказалась первым правилом, ДОСТАТОЧНО придирчиво проверенным (property-
тест на реальном масштабе), чтобы это обнажить.

**Фикс** (тот же файл, `arbitrate_spatial_with_cam`): каждая полоса
по-прежнему арбитрирует СВОЙ ПОЛНЫЙ core-набор целиком (это ОБЯЗАТЕЛЬНО —
первая попытка фикса разделяла core на "safe"/"at_risk" ДО арбитража,
из-за чего два core-матча ОДНОЙ полосы, близких к границе, переставали
сравниваться друг с другом — новый баг вместо старого, найден и исправлен
в процессе). Из УЖЕ ПРИНЯТЫХ результатов каждой полосы:
- `safe_margin = margin + reach`: матчи с `dist >= safe_margin` от ОБЕИХ
  границ доказанно недостижимы НИКАКИМ boundary-матчем (худший boundary,
  `dist=margin-1`, пишет максимум до `margin-1+reach = safe_margin-1`) —
  финальны, без дальнейших проверок.
- Остальные core-победители (`at_risk_accepted`, ширина зоны риска ровно
  `reach`, обычно малая доля от всех матчей) идут ОДНИМ дополнительным
  проходом `arbitrate_with_cam` вместе с `boundary`, как сырые кандидаты —
  тем же детерминированным тотальным порядком.

Первая (наивная) версия фикса сливала ВСЕ core-матчи обратно в этот
дополнительный проход — корректно, но измеренная регрессия ~30-50% на
CA-пробке (300×300, `reach=1`, где риска в принципе никогда не было).
Текущая (targeted) версия — в пределах шума от исходной производительности
(~9.6-14.1мс vs исходных ~8-11.5мс на той же пробке).

**Проверено и на `cam`** (не только `recursion`) — единственное другое
расширение с affected-регионом, физически способным дотянуться дальше
одной клетки от анкора, и с ПРИНЦИПИАЛЬНО другим путём вычисления (точный
`[found, magnet]`, не консервативный union дисков): `src/engine/tests.rs`'s
`test_arbitrate_spatial_matches_centralized_cam_dense_overlapping_writes` —
`radius=1`, `CamPositions` подставлены вручную так, что anchor `x`'s
найденная цель == anchor `x+1`'s собственная позиция (гарантированная
2-клеточная коллизия для каждой соседней пары, >4096 матчей). Сабо­таж-
верифицирован (реинтродукция исходного blind-union бага немедленно
поймана). Подтверждает: `reach`, взятый из консервативного
`RuleData::bbox`, остаётся корректной верхней границей для ТОЧНОГО `cam`
affected-региона (поиск физически не может найти цель дальше `radius` от
анкора) — фикс обобщается на оба класса расширений, не только на то, где
был впервые найден.

**Систематически проверены ВСЕ расширения модели** на тот же класс бага
(плотная гарантированная коллизия, >4096 матчей, сабо­таж на исходном коде):
- **Обычный одиночный сдвиг** (без recursion/cam/feedback) — тоже поймал
  баг (1200 vs 1219) — САМЫЙ частый случай в принципе, не узкий
  recursion-специфичный edge-case. Прямое следствие: CA-"пробка", которую
  эта сессия гоняла весь день ради замеров производительности, могла всё
  это время тихо принимать конфликтующие записи — сверялось только время.
- **`feedback`** — тоже поймал баг (1626 vs 1654) — единственное
  расширение с собственной (не generic) веткой в `get_match_affected_cells`.
- **`keep_source`**/**`broadcast`** — не тестировались отдельно, проверено
  чтением кода: оба идут через ТОТ ЖЕ generic-путь, что и обычный сдвиг
  (не отдельную exact-vs-conservative ветку, как cam/feedback) — фикс
  работает на геометрии (`dist` vs `margin`/`safe_margin`), не на
  конкретном значении `reach`, plain-shift-тест уже подтверждает механизм.
- **`starvation_after`/`memory`/`max_activations`** — не меняют
  `get_match_affected_cells`'s вычисление клеток вообще (только priority
  или pre-arbitration гейтинг) — не новый геометрический риск.
- Итог: все различимые пути вычисления affected-региона (generic
  write_cells, cam exact, feedback exact) проверены и защищены.

**Остаточный теоретический риск, не закрытый фиксом** (не воспроизведён ни
на одном тесте, но и не доказан невозможным): если `at_risk`-победитель
полосы проигрывает boundary-конкуренту в финальном проходе, а внутри его
же полосы был более слабый кандидат на ТУ ЖЕ клетку, отвергнутый ещё на
этапе локального арбитража полосы, — этот более слабый кандидат уже не
переигрывается, хотя в истинном централизованном порядке мог бы
унаследовать клетку. Требует отдельного целевого property-теста, если
кто-то захочет закрыть окончательно.

**Известная асимметрия по-прежнему НЕ исправлена (осталась как была):** на
регулярной (периодической) нагрузке (например, сплошной CA-сдвиг) boundary
— не пропорциональная доля работы: ~32% матчей, но 60-74% совокупного
времени core+boundary (измерено на CA-пробке 300×300, 24 полосы). Причина
— boundary последовательный, core параллельный на N потоках. Эта проблема
и попытка её решить (рекурсивное деление boundary) — ОТДЕЛЬНЫЙ вопрос от
бага выше, не связаны напрямую.

**Почему не исправлено рекурсивным делением boundary** (пробовали дважды):
рекурсивное применение того же `arbitrate_spatial_with_cam` к `boundary`
математически корректно по той же Lemma 6, но **не сходится** на
регулярных паттернах — border-границы каждого следующего уровня рекурсии
считаются той же формулой (`spread/num_bands`), и на равномерно заполненной
решётке новый boundary почти точно ложится на позиции границ следующего
уровня (резонанс периода паттерна с периодом band-split) — множество не
уменьшается, реальный прогон дал **stack overflow**. Депт-ограниченная
версия с jitter'ом (чередование числа полос по чётности уровня рекурсии)
terminates безопасно и корректна (полный suite зелёный), но контролируемый
A/B реального выигрыша не дал (arbitrate не изменился, apply даже чуть
хуже — лишний rayon-диспетчинг/аллокации на уровень рекурсии стоят больше,
чем экономит jitter). Обе попытки полностью откачены.

## 6. Горячий путь: персистентность и аллокации

Общий паттерн, найденный и исправленный несколько раз за разные буферы:
**свежий `Vec`/`HashMap` на каждый вызов горячей функции** — там, где число
вызовов за тик велико (по одному на матч или на полосу), стоимость
аллокации доминирует над полезной работой.

- **`Engine`-персистентные поля** (однопоточный вызывающий код):
  `write_buffer` (`applicator.rs`), `pattern_buffer` — `.clear()` вместо
  `Vec::new()`/`HashMap::new()` на каждый вызов, передаются как `&mut`.
- **`thread_local!`-персистентные буферы** (когда владеющая функция
  вызывается ПАРАЛЛЕЛЬНО через rayon — `Engine`-поле сюда физически не
  подходит, один буфер не может быть общим mutable-состоянием нескольких
  потоков одновременно): `USED_CELLS_BUF`/`AFFECTED_BUF`/`KEYED_BUF` в
  `arbitrate_with_cam` (`arbitrator.rs`) — каждый rayon-воркер держит свой
  персистентный буфер, переживающий вызовы между полосами И между тиками на
  этом же потоке (thread pool долгоживущий).
  - `.clear()` в начале каждого использования буфера **не всегда
    load-bearing** — например, для `KEYED_BUF` он доказуемо избыточен
    (тот же `.drain(..)` в конце функции уже безусловно опустошает буфер к
    следующему вызову), но оставлен как defensive-практика. Для
    `USED_CELLS_BUF`/`AFFECTED_BUF` он строго обязателен (диверсия ломает
    20 тестов) — буфер не дренируется, только читается/пишется по ключу.
- **`HeadRuleIndex`** (`[Option<&Vec<Rule>>; 256]`, `engine/mod.rs`) —
  замена `rule_index.get(&head)` там, где вызывается на каждый матч.
  `CellType` оборачивает `u8` (256 значений) — хэширование не нужно
  вообще, прямая индексация. Строится один раз ЗА ВЫЗОВ горячей функции
  (`build_head_index`), НЕ персистентное поле `Engine` — заимствует у
  `rule_index`-параметра, персистентность потребовала бы самоссылающейся
  структуры (сознательно избегается во всём проекте, без `unsafe`/
  `ouroboros`).
  - **`RuleDataCache`** (`conflict_analyzer.rs`) — та же проблема
    хэширования, была `HashMap<(CellType, usize), RuleData>`, ТЕПЕРЬ тоже
    `[Option<Vec<RuleData>>; 256]` (закрытый follow-up). В отличие от
    `HeadRuleIndex` — не эфемерная, а ВЛАДЕЮЩАЯ структура, персистентное
    поле `Engine::rule_cache`, перестраивается только при смене состава
    правил (`rebuild_rule_cache`), не каждый тик — самоссылающейся
    структуры здесь нет, `build_rule_data_cache` просто строит владеющий
    массив заново. Измерено на CA-пробке поверх уже применённого
    `HeadRuleIndex`+`mimalloc`: arbitrate/apply ещё немного ниже
    (~10-12мс/13-15.5мс → ~8-11.5мс/10-12.4мс).
- **Глобальный аллокатор** — `mimalloc` (`lib.rs`, `#[global_allocator]`),
  не системный. После всех точечных персистентных буферов выше тик всё
  ещё заметно упирается в malloc/free как таковой (~30-40% на всех трёх
  фазах тика на CA-пробке) — многие оставшиеся аллокации (например,
  `AffectedRegion::written_cells`, по одному на матч) не устранимы простым
  переиспользованием контейнера без нарушения публичного API
  (`apply_matches` должен возвращать `Vec<AffectedRegion>` по значению).
  Смена аллокатора забирает бОльшую часть выигрыша, ради которого
  рассматривалась bump-арена на весь тик, почти без инвазивности.
  За фичей `mimalloc-alloc` (default-on, `Cargo.toml`) — `#[global_allocator]`
  объявляется РОВНО ОДИН РАЗ на весь финальный бинарник; `cellaria` не
  только `main.rs`, но и библиотека с публичным API, значит потребитель
  `cellaria`-как-зависимости, желающий свой аллокатор, иначе получил бы
  неразрешимый со своей стороны конфликт компиляции. `default-features =
  false` у потребителя убирает декларацию целиком.

**Не сделано, но исследовано (с оговоркой почему):**
- **SoA-раскладка решётки** (`Cell{value,born_at}` → раздельные массивы) —
  реальный выигрыш (-25.7% на чтении соседей в detect), но требует
  переписать `GridStorage`, обе реализации и весь публичный API доступа к
  клетке. Не оправдано текущим масштабом узкого места.
- **GPU+CPU async-пайплайнинг тиков** (перекрытие GPU-расчёта тика N+1 с
  CPU `cpu_fallback_resolve` тика N) — архитектурная задача сравнимого
  масштаба с §5 или крупнее, не мелкая правка. Открытый вопрос, решение не
  принято.

## 7. Статический анализ конфликтов и пространственный bypass

`conflict_analyzer::ConflictGraph` (специф. §10) — статический граф "какие
головы структурно МОГУТ конфликтовать", строится один раз при
создании/перестройке `Engine`. Два независимых потребителя:

1. **Загрузка конфига** — `analyze_conflicts()`, отчёт для пользователя
   (`main.rs` печатает "арбитраж не нужен" или список конфликтующих пар).
2. **Рантайм, каждый тик** — `Engine::conflict_partners` +
   `Engine::max_affected_radius` → `spatial_bypass_split` (см. §2 выше):
   совпадения без структурных партнёров ИЛИ без партнёров в радиусе
   `2 × max_affected_radius` от себя идут в `safe` без арбитража вообще.

**Ограничение графа, НЕ являющееся живой дырой** (проверено конкретно,
2026-08-10, не только рассуждением): `ConflictGraph` доказывает только
**write-write** непересечение (`affected_regions_overlap` сравнивает
`write_cells` только с `write_cells`), **не write-read**. На первый взгляд
это значит, что safe-матч мог бы писать туда, откуда ДРУГОЙ матч читает
через `$N`/`ChangeValue::Ref`. **На практике это НЕ достижимо при текущей
архитектуре**: `pattern_buffer` (источник значений для `$N`,
`apply_rule_buffered`, `applicator.rs:376-388`) читает ИСКЛЮЧИТЕЛЬНО через
`grid.get_cell()` — саму решётку, а не `write_buffer`. `grid` физически не
мутируется НИГДЕ внутри цикла по матчам (`apply_matches_with_cam`,
`applicator.rs:145`) — единственная точка записи в `grid` за весь тик,
`write_buffer.drain()` → `grid.set_cell()` (`applicator.rs:156`), выполняется
ОДИН раз, ПОСЛЕ того, как все матчи (оба бакета — safe И arbitrated) уже
дописали свои изменения в буфер. Значит `$N` у ЛЮБОГО матча в этом тике
физически не может увидеть ничей чужой write — решётка для всех одинаково
pre-tick вплоть до самого flush, независимо от порядка обработки матчей и
независимо от того, что доказывает граф конфликтов.

Ограничение графа реально работает не как живая уязвимость, а как
**обоснование, почему прямая запись в `grid` для safe-ветки — вместо
буфера — не рассматривается**: именно это было причиной отказа от "пути
(в)" (см. §6, VecSink) — прямая запись СДЕЛАЛА БЫ write-read риск реальным
(нарушила бы только что описанную гарантию), а буферизация в её нынешнем
виде делает риск структурно недостижимым. Если когда-либо в будущем кто-то
предложит писать напрямую в `grid` для оптимизации safe-ветки (правдоподобная
идея, уже предлагалась) — вот тогда граф придётся расширять до write-read,
не раньше.

## 8. GPU-бэкенд

`gpu/engine.rs` — `GpuEngine`, `dispatch_tick` полностью синхронный (detect
+ `rounds` раундов арбитража/apply в одном submission, один
`device.poll(Maintain::Wait)` за тик — нет перекрытия с CPU, см. §6 про
нереализованный async-пайплайнинг).

**Два пайплайна** (специф. §13.1), выбираются автоматически по составу
правил конфига — не только "статичные правила без сдвигов": v2 поддерживает
сдвиги и запись в соседа через раундовый lock-free арбитраж
(`GpuRuleTable::needs_arbitration`).

**Гибридный fallback** (специф. §13.2) — длинные конфликтные цепочки,
не сошедшиеся за `rounds` раундов на GPU, доигрываются на CPU
(`cpu_fallback_resolve`); после — GPU-side `match_state` буфер обязан быть
обновлён финальным ACCEPTED/REJECTED (исторический баг — доигранные на CPU
матчи навсегда оставались PENDING(0) для `update_starvation_pass`).

**Персистентные буферы для межтикового состояния** (специф. §13.3) —
`starvation_after`/`feedback`/`memory` хранят состояние в
storage-буферах, которые НИКОГДА не очищаются между тиками (в отличие от
большинства GPU-буферов, живущих один тик) — тот же принцип, что
`thread_local!`/`Engine`-персистентность на CPU (§6), но на уровне
GPU-памяти, а не Rust-памяти.

**Подмножество, которого GPU НЕ поддерживает** — `gpu/rule_table.rs`,
`GpuUnsupportedReason` (см. таблицу §4 выше и специф. §13.4).

## 9. Самомодификация (`RuleStore`)

`rule_store.rs` — wire-протокол для добавления/удаления правил во время
работы движка. Формат пакета — байт-ориентированный, с историческими
ограничениями формата (см. doc-комментарии констант `TERMINATOR`/маркеров
опкодов в файле — например, priority 240 физически невозможно закодировать
в обычном `AddRule`, приоритет 255 недостижим вообще). Расширенный формат
`AddRuleExtended` (маркер `0xF2`) кодирует `cam`+`recursion`; `feedback`/
`memory`/`keep_source` протоколом НЕ кодируются вообще (сериализатор
возвращает `Err`, не портит данные тихо) — единственные три расширения
модели, недостижимые через самомодификацию.

`Engine::enable_self_modification()` / `enable_guarded_self_modification()`
— второй режим ограничивает самомодификацию head-id владением (не любой
матч может менять любую голову) — специф. §12.

## 10. Сохранение и воспроизведение состояния

`Engine::snapshot()`/`from_snapshot()` — полное состояние (`grid`,
`rule_index`, весь `RuleStateStore`, self-mod состояние) через
`EngineSnapshot<S>`. Сериализация — **`serde_yaml`, не `serde_json`**: у
модели данных нестроковые ключи `HashMap` почти всюду (`(x,y)`,
`(head, rule_idx)` и т.п.), которые `serde_json` не умеет сериализовать в
принципе. Единственное исключение — `TickLogEntry` (плоская структура без
нестроковых ключей), которая использует `serde_json` штатно.

`Engine::replay(snapshot, log, target_tick)` — восстановление +
проигрывание журнала входных событий вперёд. Обязан вызывать
`apply_input()` на каждом воспроизводимом тике сам (см. §2 — Input не
автоматический).

## 11. Открытые архитектурные вопросы

Все пункты, поднятые предыдущей версией этого списка, разобраны и закрыты
(2026-08-10) — либо реализацией, либо намеренным окончательным решением НЕ
делать, с обоснованием. Ничего не осталось "просто открытым" без вердикта.

**1. Рекурсивное деление boundary-полосы (§5) — закрыто, НЕ делать.**
Испробовано ДВА разных подхода:
- Наивная безусловная рекурсия — ломается на регулярных (периодических)
  паттернах (резонанс периода паттерна с периодом band-split), реальный
  прогон дал stack overflow.
- Депт-ограниченная (`MAX_BAND_SPLIT_DEPTH=4`) версия с jitter (чередование
  числа полос по чётности уровня рекурсии, чтобы сбить резонанс) —
  терминацию гарантирует, корректность подтверждена полным suite (включая
  property-тесты spatial-vs-централизованный арбитраж), но контролируемый
  A/B на CA-пробке реального выигрыша не показал: arbitrate практически не
  изменился, apply даже немного хуже — лишний rayon-диспетчинг и
  Vec-аллокации на каждом уровне рекурсии стоят больше, чем экономит
  jitter. Обе попытки полностью откачены; код `arbitrator.rs` вернулся к
  простому нерекурсивному boundary. Другой алгоритм (не рекурсия по той же
  функции) потребовался бы для реального выигрыша, если он вообще
  существует — не переоткрывать эти два конкретных подхода без новых
  данных.

**2. Протокол самомодификации: приоритеты 240/241/242 — закрыто, ОКАЗАЛОСЬ
УЖЕ РАБОТАЕТ.** Изначальная формулировка этого пункта ("зарезервированные
приоритеты 240/255, фикс ломает формат") была НЕТОЧНОЙ — перепроверка кода
показала, что `serialize_add_rule`'s `needs_ext` (`rule_store.rs:921-925`)
уже автоматически переключается на формат `AddRuleExtended`, когда
`priority` совпадает с `OP_REMOVE`/`OP_CLEAR`/`OP_ADD_EXT` (240/241/242) —
приоритет там передаётся ОТДЕЛЬНЫМ байтом, не как дискриминатор пакета,
коллизии нет. Уже покрыто существующим тестом
(`test_serializer_auto_switches_to_extended_format_for_reserved_priorities`,
`rule_store_tests.rs:867`) — полный round-trip сериализация→десериализация,
подтверждённый для всех трёх значений. Ничего чинить не нужно было.
**Приоритет 255 (0xFF) остаётся недостижим** — но это ГЛУБЖЕ, чем проблема
приоритета: `find_terminator` сканирует ПЕРВЫЙ байт `0xFF` в сыром потоке
как границу пакета ДО разбора, значит НИКАКОЙ байт полезной нагрузки
(priority, id, шаг сдвига, dx/dy/value) не может равняться 255 — не только
priority. Фикс потребовал бы byte-stuffing/escaping через весь формат, не
точечной правки — оставлено как есть, задокументировано в
`rule_store.rs`'s doc-комментариях у `OP_REMOVE`, не оправдано без
конкретной нужды.

**3. GPU+CPU async tick pipelining (§6, §8) — закрыто, решено НЕ делать
сейчас.** Реальный потенциал для arbitrate-доминантных (CA-подобных)
сценариев (перекрытие GPU-расчёта тика N+1 с CPU `cpu_fallback_resolve`
тика N), но требует прототипа (двойная буферизация состояния решётки,
синхронизация async GPU submission с CPU fallback) сравнимой сложности с
самым рискованным экспериментом этой сессии (VecSink, который не
окупился). Осознанное решение: не начинать без отдельного дизайн-прохода и
конкретной нужды, не наугад в рамках той же сессии, что уже дважды
проверяла похожие гипотезы на прочность и обе не подтвердила.

**4. SoA-раскладка решётки (§6) — закрыто, решено НЕ делать.**
`Cell{value,born_at}` → раздельные массивы — реальный, измеренный выигрыш
(-25.7% на изолированном чтении соседей в detect), но требует переписать
`GridStorage`, обе реализации (`VecStorage`/`ChunkStorage`) и весь
публичный API доступа к клетке (`grid.get_cell() -> Option<&Cell>`
физически не может остаться таким при раздельных массивах). Рассмотрена
ОДНА более дешёвая альтернатива (сузить `born_at: u64` до `u32`, вдвое
меньше сама структура `Cell`, без переписывания `GridStorage`) — отклонена
без реализации: тоже breaking (`pub born_at`), нулевой измеренный выигрыш
(идея, не проверенная гипотеза), и вносит риск молчаливого переполнения
после ~4 млрд тиков непрерывной работы. Не оправдано без реального
измерения масштаба выигрыша.

**5. Остаточный теоретический риск в исправленном boundary-vs-core (§5) —
ОТКРЫТ, не закрыт.** После фикса реального бага (boundary молча
пересекался с core) остаётся один непроверенный, не воспроизведённый
сценарий: `at_risk`-победитель полосы, проигравший boundary-конкуренту в
финальном merge-проходе, не даёт шанса более слабому кандидату СВОЕЙ ЖЕ
полосы (отвергнутому ещё на этапе локального арбитража полосы) переиграть
за освободившуюся клетку — истинный централизованный порядок мог бы
выбрать именно его. Ни один property-тест этой сессии (включая
целенаправленный recursion-репро) это не поймал — не значит, что сценарий
невозможен, значит только, что сгенерированные данные его не задели.
Нужен отдельный, целенаправленно сконструированный тест (три конкурента на
одну клетку: победитель полосы, boundary-конкурент с более высоким
приоритетом, и more слабый locally-rejected кандидат той же полосы), если
кто-то захочет закрыть это до конца, а не просто знать о риске.

Закрытые ранее пункты (были в этом списке, реализованы — не переоткрывать):
`rule_cache: RuleDataCache` переведён на массив (§6, тот же приём, что
`HeadRuleIndex`); `#[global_allocator]` вынесен за default-on фичу
`mimalloc-alloc` (§6) — не ломает потребителей `cellaria`-как-библиотеки.
