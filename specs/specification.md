# Спецификация Cellaria

**Вычислительная модель на принципе локальной редукции.**

Состояние двумерной решётки изменяется только замещением локально-связанной
группы ячеек по фиксированному правилу. Нет процессора, нет шины, нет общей памяти.
Правила — это данные. Жадный арбитраж с приоритетом и возрастом.
Цепочечный сдвиг — единственный способ перемещения данных.
Граничный ввод-вывод через каналы.

---

## 1. Принцип

Локальная редукция — состояние системы изменяется исключительно через замещение
локально-связанной группы ячеек по фиксированному правилу.

### 1.1. Чем это не является

**Не клеточный автомат.** Одно правило на всех — нет. Правил много, они разные,
они конкурируют. Конфликт разрешается жадным арбитражем:
приоритет → возраст ячейки → координаты.

**Не машина Тьюринга.** Нет отдельной головки и отдельной ленты.
Головка и данные — одно и то же: и то и другое — ячейки на решётке.
Движение — цепочечный сдвиг. Чтение и запись — та же редукция.

**Не Interaction Nets.** Там граф и порты. Здесь двумерная решётка
и физическое соседство. Адресации нет.

**Не P-системы.** Там иерархия мембран. Здесь однородная решётка.
Все ячейки равны.

## 2. Пять аксиом

Это отсечки. Если решение нарушает аксиому — оно неверно.

### 2.1. Аксиома 1: Решётка однородна

Ни одна ячейка не имеет привилегий по координате. Нет системных зон.
Нет зарезервированных областей.

- **Почему:** привилегированная зона внутри решётки — это замаскированная
  общая память. Нарушает локальность.
- **Что запрещено:** любая фиксированная область для системных нужд.
- **Что разрешено:** каналы. Канал — честная граница: данные покидают решётку
  или входят в неё. Это внешний мир, не привилегия внутри.

### 2.2. Аксиома 2: Вычисление — только через правила

Любое изменение состояния внутри решётки проходит через
detect → arbitrate → apply.

- **Почему:** второй механизм изменения конкурирует с правилами за одни и те же
  ячейки. Арбитраж о нём не знает. Детерминизм ломается.
- **Что запрещено:** любой скрытый механизм, меняющий состояние ячейки без
  участия правила.
- **Что разрешено:** возраст ячейки. Это пассивная информация о прошлом.
  Состояние не меняет. Влияет только на арбитраж.

### 2.3. Аксиома 3: Интерфейс — только через границу

Ввод и вывод — транспорт данных через границу системы. Не вычисление.
Правила к ним не применяются.

- **Почему:** снаружи решётки нет ячеек и нет правил.
  Если ввод или вывод притворяются вычислением — граница размывается.
- **Критерий:** интерфейс vs вычисление. Меняет состояние внутри решётки —
  вычисление. Пересекает границу — интерфейс.
- **Что запрещено:** изменение граничной ячейки в обход detect.
- **Что разрешено:** фазы ввода и вывода. Они не конкурируют с правилами —
  они на границе, не внутри.

### 2.4. Аксиома 4: Правила — вне решётки

Правила хранятся и обновляются за границей системы. Внутри — только ячейки.
Обновление атомарно между тиками.

- **Почему:** правила внутри решётки могут измениться в середине тика — гонки.
  Либо требуют зарезервированной зоны — нарушение аксиомы 1.
- **Что запрещено:** хранение активных правил на решётке.
- **Что разрешено:** самомодификация через канал. Фрагменты правил выводятся
  наружу, собираются, валидируются, возвращаются новым набором. Это поток
  данных через границу, не магия внутри.

### 2.5. Аксиома 5: Очистка через правило

Если ячейка должна исчезнуть — это правило. `min_age` как условие: правило
активируется, только если центральная ячейка паттерна не менялась N тиков.

- **Почему:** скрытый механизм очистки не участвует в арбитраже. Две ячейки
  с истёкшим скрытым таймером могут конфликтовать за соседа — арбитраж об этом
  не знает.
- **Что запрещено:** любой счётчик в ячейке, который сам меняет её состояние.
- **Что разрешено:** `min_age` в правиле. Очистка участвует в detect и arbitrate
  наравне со всеми. Пользователь решает, что считать мусором.

## 3. Формальная семантика

Конфигурация — пара `(G, age, R)`, где:

- `G: ℤ² → {0..255}` — решётка, отображение координат в типы ячеек.
  `G(x, y) = 0` для почти всех `(x, y)` (конечное число активных ячеек).
- `age: ℤ² → ℕ` — возраст каждой ячейки (число тиков с момента последнего изменения).
- `R` — конечное множество правил.

### 3.1. Правило

Правило — кортеж `(id, pattern, result, shift, priority, min_age)`, где:

- `pattern ⊂ ℤ² × {0..255}` — конечное множество пар `(dx, dy, expected_type)`,
  содержащее `(0, 0, head_type)`.
- `result: pattern → {0..255}` — новые типы для ячеек паттерна.
- `shift: Option(direction, length)` — направление и длина цепочки
  (единственный механизм перемещения).
- `priority ∈ ℕ` — приоритет (выше = важнее).
- `min_age ∈ ℕ` — минимальный возраст центральной ячейки для активации.

### 3.2. Совпадение (match)

Правило `r ∈ R` совпадает в позиции `(x, y)`, если:

```
∀(dx, dy, t) ∈ r.pattern: G(x + dx, y + dy) = t
∧ age(x, y) ≥ r.min_age
```

### 3.3. Шаг (tick)

Шаг — отображение `(G, age) → (G', age')`, выполняемое в пять фаз:

**Фаза 0 — Input.** Данные из внешних буферов записываются на граничные ячейки.

**Фаза 1 — Detect.** Найти все совпадения:
```
M = {(r, x, y) | r совпадает в (x, y)}
```

**Фаза 2 — Arbitrate.** Отсортировать `M` по ключу:
```
(priority DESC, age DESC, x ASC, y ASC)
```
Жадно выбрать непересекающиеся по affected region:
- Для каждого совпадения в порядке сортировки — если его affected region
  не пересекается с уже принятыми, принять.

**Фаза 3 — Apply.** Для каждого принятого совпадения:
1. Применить `shift` (цепочечный сдвиг головки).
2. Записать `result` в соответствующие ячейки.

**Фаза 4 — Flush.** Обновить возраст:
- Затронутые ячейки → 0.
- Остальные → +1.
- Вывести данные из output-буферов.

### 3.4. Уникальность ключа сортировки

**Лемма (Уникальность).** Ключ сортировки `(priority, age, rule_id, x, y)`
уникален для каждого совпадения на одном тике.

*Доказательство.* Координаты `(x, y)` определяют центр совпадения.
Два совпадения с разными центрами имеют разные `(x, y)` → ключи различны.
Два совпадения с одинаковым центром `(x, y)` обязательно принадлежат
разным правилам, так как одно правило в одной позиции может совпасть
только одним способом (паттерн проверяется целиком). Следовательно,
их `rule_id` различны. Таким образом, полный кортеж
`(priority, age, rule_id, x, y)` уникален для каждого совпадения. ∎

**Следствие.** Уникальность ключа гарантирует детерминированный порядок
обработки совпадений на фазе Arbitrate, независимо от реализации
алгоритма сортировки.

## 4. Архитектура

### 4.1. Решётка (Grid)

Двумерная прямоугольная решётка ячеек. Каждая ячейка хранит:

- `value: CellValue` — значение типа `CellType(u8)`
- `age: u64` — количество тиков с момента последнего изменения

Размер решётки фиксирован для `VecStorage` или бесконечен для `ChunkStorage`.

### 4.2. Ячейка (Cell)

```rust
pub struct Cell {
    pub value: CellValue,  // CellValue(CellType(u8))
    pub age: u64,
}
```

- `value.0.0 == 0` — пустая/дефолтная ячейка
- `age` увеличивается каждый тик, сбрасывается при изменении ячейки правилом

### 4.3. Правило (Rule)

```rust
pub struct Rule {
    pub id: Vec<CellType>,               // паттерн для сопоставления (id[0] — центр)
    pub pattern: Vec<Vec<u8>>,           // зарезервировано
    pub shifts: Vec<Vec<ShiftSpec>>,     // группы сдвигов
    pub changes: Vec<(i32, i32, ChangeValue)>,  // изменения (dx, dy, ChangeValue) после сдвига
    pub active_only: bool,               // только для активных ячеек
    pub priority: u32,                   // приоритет (выше = важнее)
    pub min_age: u64,                    // минимальный возраст центра
    pub overflow: OverflowAction,        // действие при выходе за границу решётки
}
```

**ChangeValue** — значение, записываемое в changes:

```rust
pub enum ChangeValue {
    Literal(u8),   // числовой литерал, например 5
    Ref(usize),    // ссылка на позицию в паттерне (0-based): "$0" = Ref(0)
}
```

- `Literal(value)` — записывает фиксированное значение.
- `Ref(pos)` — копирует значение ячейки из паттерна на позиции `pos` (0 = центральная ячейка, 1 = первая справа и т.д.).
- `Ref(0)` = `$0` в YAML-конфиге.

**OverflowAction** — поведение при выходе ячейки за границу решётки:

```rust
pub enum OverflowAction {
    Discard,    // отбросить ячейку (не писать в граничный буфер)
    Write(u8),  // записать в граничный буфер с указанным типом-заменителем
}
```

По умолчанию — `Discard`.

### 4.4. Сдвиг (ShiftSpec)

```rust
pub struct ShiftSpec {
    pub direction: Direction,  // Up, Down, Left, Right
    pub steps: u32,            // количество шагов
}
```

Цепочечный сдвиг: первая ячейка паттерна (головка) перемещается на `steps`
шагов в указанном направлении. Исходная позиция очищается (устанавливается
в дефолтное значение). Если новая позиция за границей решётки — ячейка
попадает в output-буфер.

### 4.5. Граничный буфер (BoundaryBuffer)

```rust
pub struct BoundaryBuffer {
    pub direction: String,                     // "input" или "output"
    pub queues: HashMap<u32, Vec<Cell>>,       // канал → очередь ячеек
    pub max_queue: Option<u8>,                 // макс. размер очереди (None = без ограничения)
}
```

- **Input-буфер:** данные извне ставятся в очередь, на фазе input следующего
  тика записываются на граничную ячейку.
- **Output-буфер:** ячейка, вышедшая за границу через сдвиг, попадает в очередь
  output-буфера.
- **max_queue:** если очередь превышает `max_queue` — при записи удаляется
  самый старый элемент (`pop_front`). Это позволяет использовать буфер
  как кольцевой без потери новых данных.

**Методы:**

- `enqueue(channel, cell)` — записать ячейку в очередь; если `queue.len() >= max_queue`,
  удаляется первый элемент.
- `dequeue(channel)` — извлечь все ячейки из очереди канала.
- `clear()` — очистить все очереди.

### 4.6. Хранилище решётки (ChunkStorage)

Помимо фиксированного `VecStorage` (прямоугольный массив `width × height`),
Cellaria поддерживает бесконечную решётку через `ChunkStorage`.

**Устройство:**
- Решётка делится на чанки размером `CHUNK_SIZE × CHUNK_SIZE` (64 × 64).
- Чанки загружаются лениво: при первом обращении к ячейке в чанке он создаётся.
- Неактивные чанки (содержащие только дефолтные ячейки) автоматически удаляются
  при записи дефолтного значения в последнюю активную ячейку чанка.

```rust
pub struct ChunkStorage {
    pub chunks: HashMap<(i64, i64), Chunk>,
    pub chunk_size: u32,  // = 64
}

struct Chunk {
    pub cells: Vec<Cell>,  // размер chunk_size × chunk_size
}
```

**Методы (через trait GridStorage):**
- `get(x, y)` — получить ячейку; если чанк не загружен — возвращает `None`.
- `set(x, y, cell)` — записать ячейку; если чанка нет — создаётся новый.
- `remove_cell(x, y)` — установить ячейку в дефолтное значение; если чанк
  стал пустым — удаляется из `chunks`.
- `active_cells()` — итератор по всем не-дефолтным ячейкам с учётом границ чанков.
- `is_active_cell(x, y)` — проверка, не является ли ячейка дефолтной.

**Стратегия выгрузки:** чанк автоматически выгружается при вызове `remove_cell`,
когда `chunk.cells.is_empty()`. Повторная загрузка происходит при первой записи
в ячейку этого чанка.

## 5. Пять фаз тика

Каждый тик симуляции состоит из пяти последовательных фаз:

### 5.1. Input (фаза 0)

Данные из input-буферов границ записываются на соответствующие граничные ячейки.
Берётся последнее значение из очереди канала 0 (если есть).

### 5.2. Detect (фаза 1)

Обход всех ячеек решётки. Для каждой ячейки проверяется:
- Совпадает ли её тип с `id[0]` какого-либо правила
- Достаточен ли возраст (`age >= min_age`)

Если совпало — проверяется полный паттерн `id[0..n]` по горизонтали.
Если весь паттерн совпал — создаётся `RuleMatch`.

**Оптимизация:** если есть правило с `active_only: true`, обход ограничивается
окрестностью активных (не-дефолтных) ячеек.

### 5.3. Arbitrate (фаза 2)

Из всех найденных совпадений выбирается непротиворечивый набор:
- Совпадения сортируются по приоритету (высший → низший), затем по возрасту
  центральной ячейки (старше → младше)
- Если два совпадения перекрываются по ячейкам — побеждает то, что выше
  в порядке сортировки
- Результат — список `accepted` совпадений

### 5.4. Apply (фаза 3)

Для каждого принятого совпадения:

1. **Сдвиги:** для каждой группы сдвигов из `rule.shifts` применяется
   цепочечный сдвиг первой ячейки паттерна (головки). Если групп несколько —
   применяются последовательно.
2. **Изменения:** для каждого `(dx, dy, value)` из `rule.changes`:
   - Вычисляется после-сдвиговая позиция: `(cx + total_dx + dx, cy + total_dy + dy)`
   - Если координаты в пределах решётки — ячейка устанавливается в новое значение
   - `total_dx, total_dy` — суммарный сдвиг от первой группы сдвигов

**Важно:** сдвиги применяются ДО изменений. Изменения накладываются на
после-сдвиговую позицию головки.

### 5.5. Flush (фаза 4)

- Сбор данных из output-буферов границ в выходной список
- Увеличение возраста всех ячеек на 1 (`advance_age`)
- Сброс возраста для ячеек, затронутых правилами

## 6. Цепочечный сдвиг

Цепочечный сдвиг — единственный механизм перемещения данных в Cellaria.

**Алгоритм:**
1. Берётся только первая ячейка паттерна (головка) по координате `(cx, cy)`
2. Вычисляется новая позиция: `(cx + dx * steps, cy + dy * steps)`
3. Если новая позиция в пределах решётки — головка копируется туда
4. Если новая позиция за границей — головка помещается в output-буфер
   ближайшей граничной ячейки
5. Исходная позиция `(cx, cy)` очищается (дефолтная ячейка)
6. Остальные ячейки паттерна НЕ сдвигаются

**Обоснование:** в модели Cellaria паттерн `id[0..n]` читается как
"головка + хвост". Головка — активный элемент, который движется.
Хвост — статические данные, которые остаются на месте.

---

## 7. Арбитраж

Жадный алгоритм разрешения конфликтов:

1. Все совпадения сортируются по ключу: `(priority DESC, age DESC, x ASC, y ASC)`
2. Для каждого совпадения в порядке сортировки:
   - Проверяется, не занята ли центральная ячейка
   - Проверяется, не занята ли ни одна из ячеек паттерна
   - Если все свободны — совпадение принимается, ячейки помечаются занятыми

---

## 8. Ввод-вывод (IO)

### 8.1. Ввод (Input)

- Данные подаются через `push_input(channel, value)`
- На фазе input следующего тика значение записывается на граничную ячейку
- Правило может обнаружить новое значение и примениться

### 8.2. Вывод (Output)

- Когда головка выходит за границу решётки при сдвиге, она попадает
  в output-буфер
- Данные извлекаются через `pop_output()`
- На фазе flush output-буферы опустошаются

### 8.3. Каналы

- Input и output буферы организованы по каналам (u32)
- Канал 0 используется по умолчанию
- Максимальный размер очереди задаётся в конфиге (`max_queue`)

## 9. Доказательство тьюринг-полноты

Мы приводим два независимых доказательства:

1. **Прямая эмуляция:** конструктивный алгоритм перевода произвольной машины
   Тьюринга в набор правил Cellaria.
2. **Сведение через tag system:** tag system (Minsky, m=2) тьюринг-полна,
   шаг tag system моделируется одним прогоном Cellaria.

---

### 9.1. Путь 1: Прямая эмуляция машины Тьюринга

#### 9.1.1. Конструктивный алгоритм перевода

Дана произвольная машина Тьюринга:

- Алфавит ленты: `Γ` (включая пустой символ `⊔`)
- Множество состояний: `Q`
- Функция перехода: `δ : Q × Γ → Q × Γ × {L, R, H}`

**Кодирование в решётку Cellaria (1×N):**

| Компонент ТМ | Кодировка в Cellaria |
|---|---|
| Символ ленты `a ∈ Γ` | Тип ячейки `t(a) ∈ {1..K}` |
| Пусто `⊔` | Тип `0` |
| Состояние `q ∈ Q` | Тип-маркер головки `h(q) ∈ {10..10+\|Q\|-1}` |
| Головка в состоянии `q` над символом `a` | Паттерн `[h(q), t(a)]` |

**Алгоритм:**

1. Для каждой пары `(q, a) ∈ Q × Γ`:
   - Вычислить `δ(q, a) = (q', a', d)`
   - Создать правило:
     ```
     id: [h(q), t(a)]
     shifts:
       - group:
           - direction: east    # если d = R
             steps: 1
           - direction: west    # если d = L
             steps: 1
     changes:
       - [0, 0, t(a')]          # запись нового символа
       - [0, 0, h(q')]          # новое состояние (только если d = H)
     ```
   - Для `d = H` (остановка): shifts пуст, change только на символ.
   
2. Движение вправо (`d = R`):
   - Сдвиг east на 1 шаг
   - Change `(0, 0, t(a'))` — новый символ записывается на после-сдвиговой
     позиции головки.
   - Тип головки остаётся `h(q')` (он переходит на новую позицию вместе
     с головкой).

3. Движение влево (`d = L`):
   - Сдвиг west на 1 шаг
   - Change `(0, 0, t(a'))` — запись символа на после-сдвиговой позиции.

**Семантическое сохранение:**

- Каждый тик Cellaria соответствует ровно одному шагу ТМ.
- Паттерн `[h(q), t(a)]` детектируется только если головка `h(q)` стоит
  непосредственно слева от символа `t(a)` — это чтение.
- Change записывает новый символ на освободившуюся позицию — это запись.
- Сдвиг перемещает головку — это движение.
- Арбитраж гарантирует, что ни одно другое правило не вмешается в занятые
  ячейки, так как паттерны разных состояний не перекрываются.

Таким образом, любая машина Тьюринга переводится в конечный набор правил
Cellaria, и трасса симуляции изоморфна трассе ТМ.

#### 9.1.2. Пример: конфиг turing.yaml

Конфиг `configs/turing.yaml` реализует частный случай — инвертирование
битов на ленте (описан в секции 9.1.1).

| Машина Тьюринга | Cellaria |
|---|---|
| Головка | Ячейка типа 5 (вправо) / 6 (влево) |
| Лента | Последовательность ячеек типов 0/1 |
| Функция перехода | Правила `id → shifts + changes` |
| Движение вправо | Сдвиг east (dx=1) |
| Движение влево | Сдвиг west (dx=-1) |
| Чтение бита | Паттерн `[5, 0]` или `[5, 1]` |
| Запись бита | Change на после-сдвиговой позиции |
| Остановка | Правило без сдвигов |

```
id=[5, 0] → shift east, change (0,0,1)  — прочитан 0, пишем 1, вправо
id=[5, 1] → shift east, change (0,0,0)  — прочитан 1, пишем 0, вправо
id=[6, 0] → shift west, change (0,0,1)  — прочитан 0, пишем 1, влево
id=[6, 1] → shift west, change (0,0,0)  — прочитан 1, пишем 0, влево
id=[5]    → shift east, change (0,0,6)  — разворот: 5→6
id=[6]    → shift west, change (0,0,5)  — разворот: 6→5
```

### 9.2. Путь 2: Сведение через tag system

Второе доказательство использует tag system — модель, эквивалентную
машине Тьюринга по Minsky (1961).

#### 9.2.1. Определение tag system

Tag system с параметром `m = 2` и алфавитом `Σ = {A, B}`:

- Строка — последовательность символов `w ∈ Σ*`
- Шаг: первый символ `X` определяет продукцию `π(X) ∈ Σ*`
- Первые `m = 2` символа удаляются, продукция `π(X)` дописывается в конец
- Выполнение останавливается, когда длина строки меньше `m`

Продукции для нашего примера: `π(A) = AB, π(B) = A`

#### 9.2.2. Эмуляция одного шага tag system в Cellaria

Конфиг `configs/tag_system.yaml` реализует один шаг tag system.

**Схема решётки (1×32):**

```
[10, A, B, B, 0, 0, ...]
  ↑   ↑
маркер  строка
```

**Состояния маркера:**

| Тип | Смысл |
|---|---|
| `10` | Начало: читаем первый символ |
| `11` | Прочитан A, удаляем второй символ |
| `12` | Прочитан B, удаляем второй символ |
| `13` | Traverse (A→AB): переносим символы налево |
| `14` | Traverse (B→A): переносим символы налево |
| `15` | Пишем A (первый символ продукции AB) |
| `16` | Пишем A (продукция A) |
| `17` | Пишем B (второй символ продукции AB) |

**Фазы одного шага:**

1. Чтение и удаление m=2: `[10, X, Y] → [0, 0, 13|14]`
2. Traverse: `[13|14, X] → [X, 13|14]` — сжатие строки
3. Запись продукции: `[13|14, 0] → [π(X), 0]` — продукция записывается,
   маркер исчезает (change `[0, 0, 0]`). Тик останавливается,
   так как на следующем тике нет совпадений.

**Пример трассы (A B B → B A B)** — из реального запуска:

```
Тик 0: [10, 1, 2, 2, 0, ...]   A B B (1=A, 2=B)
Тик 1: [0, 11, 2, 2, 0, ...]   читаем A
Тик 2: [0, 0, 13, 2, 0, ...]   удаляем второй B
Тик 3: [0, 0, 2, 13, 0, ...]   перенос B
Тик 4: [0, 0, 2, 1, 15, ...]   пишем A (продукция AB)
Тик 5: [0, 0, 2, 1, 2, ...]    пишем B, маркер исчезает → 0 совпадений
Тик 6: [0, 0, 2, 1, 2, ...]    стабильно: B A B ✓
```

#### 9.2.3. Композиция шагов

Один шаг tag system = один прогон Cellaria с начальным состоянием
(строка + маркер 10) до состояния с 0 совпадений. Результат —
строка, подготовленная для следующего шага. Повторение шагов —
через граничный ввод-вывод: состояние решётки после шага выводится
и подаётся на вход для следующего шага. Это не нарушает аксиомы:
граничный IO разрешён аксиомой 3.

#### 9.2.4. Транзитивное замыкание

1. Tag system (m=2, алфавит 2 символа) тьюринг-полна [Minsky 1961].
2. Один шаг tag system моделируется Cellaria (конструкция 9.2.2).
3. Композиция шагов — через IO-границу (разрешено аксиомой 3).
Следовательно, Cellaria тьюринг-полна.

---

### 9.3. Вывод

Два независимых пути доказательства:

```
Путь 1:  Машина Тьюринга → Cellaria (прямая эмуляция, turing.yaml)
Путь 2:  Tag system → Машина Тьюринга [Minsky] → Cellaria (tag_system.yaml)
```

Оба пути подтверждают, что модель локальной редукции Cellaria
тьюринг-полна. Это означает, что аксиомы Cellaria (однородная решётка,
вычисление только через правила, интерфейс только через границу,
правила вне решётки, очистка через правило) достаточны для
универсальных вычислений.

## 10. Статический анализ конфликтов (Static Conflict Analysis)

### 10.1. Определение конфликта

Два правила R_i и R_j конфликтуют, если существует такая пара
позиций на решётке (позиций их головок), что:

1. Паттерны обоих правил совпадают одновременно.
2. Их affected regions (с учётом сдвигов) пересекаются.

**Определение 2 (Конфликт).** Пусть R_i и R_j — правила с паттернами
`P_i = [t_{i,0}, ..., t_{i,k_i-1}]` и `P_j = [t_{j,0}, ..., t_{j,k_j-1}]`,
где `t_{i,0}` — тип головки. Пусть `A_i` — множество ячеек, затронутых
R_i относительно позиции его головки (включает ячейки паттерна,
начальную позицию головки, конечную позицию головки после сдвигов
и ячейки изменений). Пусть `A_j` — аналогичное множество для R_j.
Правила R_i и R_j конфликтуют, если существует сдвиг `(dx, dy)` такой, что:

- Паттерны пересекаются по ячейкам, и типы в этих ячейках совместимы
  (ячейка может иметь только один тип; если оба правила требуют
  разные типы на одной ячейке, конфликта нет).
- `A_i ∩ (A_j + (dx, dy)) ≠ ∅`.

### 10.2. Лемма 1 (Несовместимость типов устраняет конфликт)

Если в любой пересекающейся ячейке паттернов требуемые типы различны,
правила не могут совпасть одновременно при данном относительном
смещении, и конфликт не возникает.

*Доказательство.* Ячейка решётки имеет ровно один тип в любой момент
времени. Если R_i требует тип `t_a`, а R_j требует тип `t_b ≠ t_a`
в одной и той же ячейке, ни одно состояние решётки не может
удовлетворить оба паттерна одновременно. Следовательно, оба правила
не могут быть активны одновременно с этим смещением,
и конфликт невозможен. ∎

### 10.3. Лемма 2 (Разные min_age устраняют конфликт)

Если `min_age(R_i) ≠ min_age(R_j)`, правила активируются в разных
временных окнах и не могут конфликтовать.

*Доказательство.* По Аксиоме 5, `min_age` гарантирует, что правило
активируется только после того, как его центральная ячейка оставалась
неизменной в течение N тиков. Правила с разными `min_age` имеют
непересекающиеся окна активации. ∎

### 10.4. Обобщённый критерий

Правила R_i и R_j бесконфликтны, если для всех возможных взаимных
смещений их паттернов выполняется хотя бы одно из условий:

1. Типы в пересекающихся ячейках несовместимы (не могут быть
   одновременно true на одной ячейке).
2. Итоговые affected regions не пересекаются.

### 10.5. Алгоритм построения графа конфликтов

**Вход:** набор правил &[Rule].

**Выход:** `ConflictGraph` с вершинами (индексы правил) и рёбрами
(конфликтующие пары).

```
для каждой пары (i, j) с i < j:
    если min_age(R_i) ≠ min_age(R_j): пропустить
    для каждого смещения (dx, dy) в пределах bounding box'ов:
        если паттерны пересекаются при (dx, dy):
            если типы в пересекающихся ячейках несовместимы:
                пропустить (не могут совпасть одновременно)
            если affected regions пересекаются:
                добавить ребро (i, j)
```

**Сложность:** O(N² · K²), где N — число правил, K — максимальный
размер affected region.

### 10.6. Теорема (Бесконфликтность ⇒ отсутствие арбитража)

Если граф конфликтов для набора правил пуст, фазу арбитража в цикле
тика можно пропустить: все совпадения применяются одновременно,
и результат эквивалентен последовательному применению.

*Доказательство.* Если граф пуст, ни одна пара правил не может
одновременно совпасть на перекрывающихся позициях. Следовательно,
все совпадения в любом тике попарно не пересекаются по affected
regions. Применение непересекающихся преобразований коммутативно
и даёт тот же результат независимо от порядка. ∎

### 10.7. Следствие (Параллельное выполнение)

Бесконфликтные наборы правил могут выполняться параллельно
(на GPU/FPGA) без изменения семантики.

### 10.8. Связь с аксиомами

Анализ конфликтов не нарушает ни одну из пяти аксиом:

- **Аксиома 1 (однородная решётка):** не вводит привилегированных зон.
- **Аксиома 2 (вычисления через правила):** не изменяет семантику
  выполнения правил.
- **Аксиома 3 (интерфейс через границу):** не добавляет новых
  интерфейсов.
- **Аксиома 4 (правила снаружи):** работает со статическим набором
  правил, не затрагивая RuleStore.
- **Аксиома 5 (очистка через правила):** корректно разделяет правила
  с разными `min_age`.

```yaml
grid:

rules:
  - id: [t1, t2, ...]

    min_age: 0
    active_only: false
    shifts:
      - group:
          - direction: east
            steps: 1
    changes:
      - [dx, dy, value]
```

## 12. Самомодификация (RuleStore)

Правила могут обновляться в рантайме через канальный протокол:

1. Фрагменты правил выводятся через output-канал в виде байтовых пакетов
2. Внешний обработчик собирает, валидирует и возвращает новый набор правил
3. RuleStore применяет изменения атомарно между тиками

Формат пакета:
- `<priority>, <id_len>, [id_bytes...] [, shifts...] [, changes...], 0xFF` — добавить правило
- `0xF0 + id` — удалить правило с id
- `0xF1` — очистить все правила
- `0xFF` — терминатор пакета

Пакеты с id = 255 игнорируются (зарезервировано).

**Ограничение протокола:** в изменениях (`changes`) поддерживается только
`ChangeValue::Literal`. Ссылочные изменения (`ChangeValue::Ref`, например `$0`)
не кодируются в пакетах и будут отклонены парсером.
